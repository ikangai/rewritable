# Security Policy

## Reporting a vulnerability

Please report security issues privately. Do **not** open a public GitHub issue for a vulnerability.

**Preferred:** open a [GitHub security advisory](https://github.com/ikangai/rewritable/security/advisories/new)
on this repository. That keeps the report private until a fix is ready and gives us a place to
coordinate with you.

**Alternative:** email `hello@ikangai.com` with `SECURITY` in the subject line.

Please include what you need to make the issue reproducible — the affected component, the version or
commit, and the steps. If you have a proof of concept, attach it rather than pasting it anywhere
public.

**Response expectations.** This is a small project. We aim to acknowledge a report within 7 days and
to tell you whether we consider it in scope within 30 days. We will let you know when a fix ships,
and we are happy to credit you unless you would rather we didn't.

## Scope

Three components, with different trust models. Please say which one you are reporting against.

**1. The container runtime (`seeds/rewritable.html`) and emitted `.html` files.**
A rewritable is a single self-contained HTML file that renders, edits, and exports itself, and calls
a model through a user-supplied API key. In scope: escaping the frozen-zone / bootstrap-immutability
guarantees; the edit-protocol validators (`rwa-edit/1`); the skill and vault layers (Worker
isolation, permission tiers, the credential store); the signed-agent verification path; anything
that lets a document's own content reach a capability it should not have.

**2. The CLI (`cli/`, npm package `rewritable`).**
In scope: command injection, path traversal, SSRF in the network-bearing commands (`rwa clone`,
`rwa publish`, `rwa publish-site`, `rwa host`), and prompt-injection paths that reach a shell.

**3. The hosted service (`service/`, `rewritable.ikangai.com`).**
In scope: cross-share isolation, authentication on the `/share` and `/r/` route families, and the
server-authoritative apply path.

## Known and accepted risks

These are documented design positions, not undiscovered bugs. Reports restating them are welcome as
discussion, but they are already known:

The threat model for received containers is written up in full, including the mitigations considered
and why some were rejected: [`docs/received-container-threat-model-2026-08-04.md`](docs/received-container-threat-model-2026-08-04.md).

- **A rewritable executes its own inline `<script>` on every render.** Interactive documents are an
  intended feature. A container you received from someone else runs their code in your browser, in
  the same realm as the runtime. **This is an accepted risk, decided deliberately** — sandboxing the
  document body would mean giving up interactive documents. It is documented in `README.md` under
  "Opening a rewritable someone sent you" so users can make an informed choice.
- **Under `file://`, all containers share the null origin.** Per-container IndexedDB namespacing by
  `DOC_UUID` is a naming convention, not a security boundary. This is stated in the container spec
  (§5.7). The fix that closed the equivalent hosted problem — one origin per share — has no local
  analogue.
- **There is no CSP on the document realm.** Deliberately deferred, because the seed is itself an
  inline-script design. The CSP that does ship is worker-scoped: it stops a skill Worker importing
  remote code. It governs script *origin*, not capability.
- **The API key lives in `sessionStorage`,** never persisted to disk and never written into the
  exported file — but it is readable by script running in the same realm.
- **The vault key is not persisted.** It lives only in a closure, re-prompts after a reload, and
  auto-locks after idle. It was previously cached in `sessionStorage` so an unlocked vault survived
  a reload; that was removed in favour of the re-prompt.

If you have found a way to make one of these materially worse than described, that **is** in scope —
please report it.

## Out of scope

- Vulnerabilities in a document a user authored or pasted themselves.
- Findings against the vendored third-party libraries in `cli/skills/` or `service/public/`; report
  those upstream.
- Reports generated by automated scanners with no demonstrated impact.
