# Workflow v0.3 — iteration tightening (pin / dirty / test-step)

**Date:** 2026-05-19
**Goal:** make the linear-pipeline iteration loop ~10× tighter without
spec changes or new layers.
**Inspired by:** the n8n editor's `pinData` / dirtiness / "test-step"
trio (`docs/plans/2026-05-19-n8n-editor-survey.md` if we ever
formalize the survey; for now see the conversation that spawned this
plan).
**Pre-req status:** workflow v0.2 Phase 6 verified
(`docs/plans/2026-05-18-workflow-v0.2-phase6-findings.md`); 0
substrate fixes pending.

## Goal in one sentence

Land three per-step affordances — **pin output**, **dirtiness
indicator**, **test-this-step button** — as one bundle in the
workflow product's frozen runner block + CSS, with three new
conformance scenarios and a tightened system prompt. Single seed
change; no spec change; no new tools.

## Non-goals (deferred to v0.4+)

- Schema-style output preview (rendering `key: type` tree instead of
  raw JSON). Worth doing but separate concern; keep this PR focused.
- Auto-derived subtitle ("POST → /users" style). Cute but needs
  light AST-poking on the script body — out of scope.
- Per-step output toggle (table | json | schema). Same — output
  rendering is a separate v0.4 concern.
- Iteration count badge `(×N)`. Linear pipelines don't loop in v0.3.
- Tab-to-add-step UX. The lens already handles inserts; gesture
  polish is v0.4.

## Mental model

Three per-step `<li>` attributes carry the new state. All three live
inside `INLINE_DOC`, so ⌘S preserves them and the agent's
`apply_edits` envelopes already touch them naturally (the existing
"preserve `data-rwa-id`" rule generalizes).

| Attribute | Type | Set by | Cleared by | Meaning |
|---|---|---|---|---|
| `data-pinned-output` | JSON string | user clicking 📌 | user clicking 📌 again | runner short-circuits `run()` and returns this value instead |
| `data-last-output` | JSON string | runner on successful run | user toggling pin off | cached upstream value the "test-step" button feeds as `prev` |
| `data-last-run-hash` | 8-char hash | runner on successful run | code edit (becomes stale) | hash of `(stepCode + prevHash)` at last successful run; mismatch ⇒ `.stale` class |

**Pin semantics.** When `data-pinned-output` is set on step N, the
workflow runner returns its parsed value as step N's output *without
calling `run()`*. Downstream steps see it as their `prev`. The pinned
step renders with `.rwa-step.pinned` (a `📌` chip near the title) so
the state is obvious at a glance.

**Dirtiness semantics.** A step is "fresh" iff
`hash(scriptBody + prevHash) === data-last-run-hash`. `prevHash` is
either the previous step's `data-last-run-hash` (or, if that step is
pinned, the hash of its pinned output) or the literal string `init`
for step 0. Any step where the current hash differs from the stored
one renders with `.rwa-step.stale` (a `⚠` chip + yellow border tint).
Staleness cascades: if step N is stale, step N+1 reads N's *current*
hash as its `prevHash`, which will also diverge from N+1's stored
hash. The cascade falls out of the linear walk for free — no special
case needed.

**Test-step semantics.** Per-step `▶ Test` button in the hover-revealed
toolbar (mirrors n8n's per-node test action). Runs *just that step*
against the previous step's `data-last-output` (or `undefined` if step
0, or the pinned value if previous is pinned). Updates the step's
`<output>` slot, `data-last-output`, and `data-last-run-hash` on
success. Does **not** continue the pipeline downstream. The point is a
fast "did this step's code do the right thing?" loop.

## Phases

### Phase 1 — runner extension + CSS

**Files:** `cli/src/seed.mjs` (`KIND_WORKFLOW_BODY`).

Substance:

- CSS:
  - `.rwa-step.pinned` — left border `var(--blue)`, `::after`
    content `"📌"` positioned top-right of header.
  - `.rwa-step.stale` — left border `var(--yellow)`, `::after`
    content `"⚠"` (the cascade implies the user can tell at a
    glance which step in the chain went stale first).
  - `.rwa-step-toolbar` — absolutely positioned top-right strip
    holding two small buttons (`▶` test, `📌` pin). `opacity:0`
    by default; `opacity:1` on `:hover` or `:focus-within` of the
    parent `<li>`.
  - Pin chip and toolbar must not overlap; pin chip slightly
    inboard.

- Runner JS additions (still inside the frozen block):
  - `function hashStr(s) { ... }` — 32-bit polynomial hash, 8-char
    hex output. Used for `data-last-run-hash`.
  - `function stepBodyOf(li)` — returns
    `li.querySelector('script[type="text/rwa-step"]').textContent`,
    normalized (trim, collapse trailing whitespace) so cosmetic
    edits don't flip the hash.
  - Modify `runWorkflow`:
    - For each step, compute `currentHash = hashStr(stepBody +
      prevHash)` before running.
    - If `li.dataset.pinnedOutput` exists: parse, set
      `prev = parsedPin`, write to the step's `<output>` rendered
      as JSON, **mark `.done`**, do NOT update
      `data-last-run-hash` (pin is its own state). Move to next
      step.
    - Else: call `run(ctx, prev)`. On success: set
      `data-last-output = JSON.stringify(result)`,
      `data-last-run-hash = currentHash`, remove `.stale` class.
      Render output. Set `prevHash = currentHash` (or, on the
      *next* iteration if the step was pinned, `prevHash =
      hashStr(pinnedValueJson)`).
  - On boot (after DOMContentLoaded inside the runner's IIFE):
    walk steps left-to-right, compute current hash chain, compare
    to stored `data-last-run-hash` on each, apply/remove
    `.stale` class. This is the visual indicator for "you edited
    a step's code since last run."
  - Per-step test button (`▶`) click handler:
    - Find the upstream `<li>`'s `data-last-output` (or
      `data-pinned-output`, or `undefined` if first step).
    - Parse, call this step's `run(ctx, parsedPrev)`.
    - On success: update `data-last-output`,
      `data-last-run-hash`, `.done` class, output slot. Recompute
      cascade — downstream steps may go stale.
  - Pin toggle button (`📌`) click handler:
    - If `data-pinned-output` is set: remove it; remove
      `.pinned`; recompute downstream cascade.
    - Else: take current `data-last-output` (or the rendered
      output text if data attr absent), validate it parses as
      JSON, set `data-pinned-output`, add `.pinned`. Recompute
      downstream cascade.
    - If there's no output to pin: toolbar button is disabled
      (`aria-disabled="true"`).

- Empty-output rendering: when the runner writes JSON to
  `<output>`, also write the same JSON to `data-last-output` on the
  `<li>` for the test-step button to read. (Today the runner only
  writes to `<output>`; v0.3 adds the dataset write.)

**Verification:** `cd benchmark && npm run conformance` still passes
46/46 (no regression). Phase 3 adds 3 new scenarios.

**Size:** half a day.

```
Per-step state attributes — preserve verbatim when editing a <li class="rwa-step">:
  • data-rwa-id — runtime-managed stable identifier (existing rule).
  • data-pinned-output — user has pinned a frozen output for this
    step. Runtime short-circuits run() and returns this value.

    current state is how the runner detects staleness.
```

script body inside `<script type="text/rwa-step">` will
*correctly* invalidate `data-last-run-hash` — that's by design and
the agent doesn't need to update it.

### Phase 3 — conformance scenarios

**Files:** three new files under `benchmark/scenarios/conformance/`.

- **WORKFLOW-03 — pin short-circuit.** setDoc fixture: 2-step
  workflow where step 0 has `data-pinned-output='"pinned-value"'`.
  Programmatically trigger `runWorkflow`. Assert step 0's
  `<output>` contains `"pinned-value"`. Assert (via a counter or

- **WORKFLOW-04 — dirtiness detection.** setDoc fixture: 1-step

  expose the runner's `hashStr` via a known global for test

  tick.)
- **WORKFLOW-05 — test-step uses cached upstream.** setDoc
  fixture: 2-step workflow where step 0 has

  click step 1's `▶` button (or invoke the runner's
  `testStep(li)` function if exposed). Assert step 1's
  `<output>` shows `"cached-from-step-0"` — proving the test
  button fed the cached upstream value as `prev`.

For all three: anchor on the structural invariants the runner
manages, not on visual chrome. Use `setDoc` to install fixtures

## Open decisions (resolve at execution time)

1. **Pin a partial JSON?** If `data-last-output` is non-JSON (e.g.
   a step returned a Promise unintentionally and `JSON.stringify`
   returned `{}`), pinning that emptily is unhelpful. **Default:**
   require `JSON.parse(data-last-output)` to succeed and produce a
   non-`undefined` value before allowing pin. Disable the `📌`
   button otherwise.
2. **Stale cascade on a pinned step.** If a step is pinned and its
   code is edited, should the chip show `📌 + ⚠` (pinned but code
   has drifted)? **Default:** yes, show both — pin chip + stale
   border. The user wants to know "this is pinned to an old run."
   Downstream still receives the pinned value, so downstream is NOT
   stale because of this step's edit (the pin "absorbs" it).
3. **Hash collision.** 8-char hex = 32 bits = ~4B states. Collision
   on a casual edit is ~0. Acceptable. If it ever bites, bump to
   12 chars.
4. **Toolbar chrome.** Two-button strip vs single overflow menu vs
   single icon that opens a menu. **Default:** two visible icons.
   The whole point is a fast iteration loop; one click beats two.
   Hover-reveal keeps the resting state clean.
5. **Empty pinned value.** Storing `data-pinned-output=""` is
   meaningless. **Default:** absence ⇒ unpinned; presence (even
   empty string) ⇒ pinned to `null` after `JSON.parse("")` fails.
   See decision #1 — disable the button when there's nothing to
   pin.
6. **Persistence of `data-last-output` across reload.** It lives
   in INLINE_DOC so yes, it survives ⌘S+reload. This is **already
   true** for the v0.2 runner if you commit after running — but in
   practice users haven't. **Default in v0.3:** the runner ALWAYS
   writes to `data-last-output` on success, so the next ⌘S
   automatically captures last-run state. If the user wants
   "scratch" runs, they can `data-skip-cache="true"` on the `<li>`
   — but that's out-of-scope; default = always cache.

## What it won't do

- Branching / fan-out (still no graph).
- Inspect data in any view richer than JSON-stringify (Schema view
  is v0.4).
- Long-running steps with cancellation (`ctx.signal` is still
  reserved per v0.2 system prompt).
- Cross-step `data-` attribute documentation in user-facing places
  beyond the system prompt. (Could add to `cli/README.md` if it
  feels like a user-facing feature; my call is no — they're
  runtime-managed state, the user interacts via the buttons.)
