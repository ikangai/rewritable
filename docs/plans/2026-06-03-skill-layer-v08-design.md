# Skill layer v0.8 — design (leaner, realizable)

Status: design, validated in brainstorming with the author (scope = "real isolation layer").
Supersedes the unbuildable parts of `docs/specs/re-write-able-actions-spec-v0.7.md` (which stays as the
reference design). Grounded in measured browser facts (below) and an adversarial red-team of the first
synthesis. Author decision locked: **capability skills run behind mandatory Worker isolation.**

## 0. Measured constraints (real Chrome, 2026-06-03)
Probe `.claude/skill-probe.html`, run under `file://` AND a served origin:
- Blob Web Workers **spawn** under `file://` and `http(s)`; inside a fresh worker `importScripts`/`fetch`/`indexedDB`/`Worker`/`eval` all exist by default → the runtime must remove/shadow them.
- meta-tag CSP `connect-src 'none'` **is enforced** under `file://` and `http(s)` (fetch rejected). v0.7's host-CSP connect-src union is realizable via `<meta>` with no server headers, even offline.
- WebCrypto native **Ed25519** sign/verify works (no CDN lib needed).
- WebCrypto **PBKDF2 + AES-GCM** round-trips (vault encryption realizable; Argon2id optional, deferred).
- **OPFS throws SecurityError under `file://`** (works on a served origin). → durable skill state cannot use OPFS for emailed files; it lives in IDB + the file bytes.

## 1. Thesis
v0.8 is a dedicated **`skill-host` container kind** in which a user installs permission-gated skills
through one honest install dialog. The install dialog is the trust anchor (Invariant 10); everything else
is the minimum infrastructure that keeps the dialog's sentences true. The base products
(document/datatable/workflow/presentation) carry none of this. What a recipient needs to *run* a skill
travels in the file's own bytes; machine-local secrets (credentials) do not.

## 2. Architecture decisions (locked)

### 2.1 Placement — dedicated `skill-host` PRODUCT_KIND
Not baked into every seed. Generated by `rwa new --kind skill-host`. Preserves Invariant 1 (byte-identical
bootstrap) for base products and keeps them lean. New kind = one entry each in `KIND_TABLE`
(`cli/src/seed.mjs`), `SYSTEM_PROMPTS` (seed), `KIND_PROVIDERS` (`tools/self-description.mjs` +
`cli/src/identity.mjs`), `cli/README.md`, `cli/bin/rwa.mjs`. The skill-host bootstrap additionally carries
the skill runtime: keyed registry, vault, install dialog, capability scan, Worker spawner+bridge, CSP injector.

### 2.2 Execution model — EVERY skill runs in a Worker (REVISED after scenario X5)
**Both kinds run in a Worker. There is no main-thread skill path.** The earlier "compute runs main-thread
in a fresh function scope" was unsound and is deleted: a function parameter named `runtime` shadows only the
identifier `runtime`; the scope chain still resolves `window.sessionStorage` (the API key, `RWA.K_API`),
`window.indexedDB` (`rwa_vault`), `window.document`, and `window.fetch`. A "fresh function scope" is a *naming*
boundary, not a *capability* boundary — so a main-thread compute skill could steal the API key/vault and
exfiltrate via any origin a *different* installed skill opened in the page-wide CSP. (Scenario X5.)

- **`compute` skill** (zero capability): runs in a **bridgeless Worker** — dangerous globals removed, and
  **no `fetch`/`vault` bridge installed at all**. There is literally nothing to reach (`sessionStorage`,
  `indexedDB`, `document`, `fetch` do not exist in the Worker), so "zero capability" is structurally true,
  not a convention. JSON-serializable I/O, 5s timeout, spawn → invoke → terminate.
- **`tool` skill** (declares `network:` and/or `vault:`): same Worker + global removal, **plus** bridged
  `fetch`/`runtime.vault` tunneled over the message channel with a per-invocation `identity_tag`. The bridge
  is the **sole path** to network/vault; the bridge re-derives `new URL(url).origin` and matches the
  manifest's `network:` patterns on **every call** (no cached allowlist to poison). No pool.

This makes the install-dialog promise — *"a skill cannot reach an origin or vault namespace it didn't
declare"* — **true for every kind**. Cost is ~1–2 ms Worker spawn against a 5 s budget; the bridgeless path
has *less* UX than a main-thread path, not more. Globals set non-writable/non-configurable `undefined`
**before** skill code loads: `importScripts`, `Worker`, `SharedWorker`, `XMLHttpRequest`, `WebSocket`,
`EventSource`, `indexedDB`, `eval`, `Function` (+ `window` doesn't exist in a Worker). Verified vs. the real
seed in scenario X3.

### 2.3 Skill registry — a sibling to the affordance kernel, NOT `provide()` reuse
The existing kernel cannot host skills as-is (verified in seed): `runtimeProvide` **throws** on kinds other
than `view`/`edit-surface`/`compute`; slots are **single-per-kind** (`providers[kind]=spec`); `compute` is
**declarative-only** (no execution contract). So v0.8 adds a separate keyed registry:
```
installedSkills: Map<skillId, { skillId, manifest, code, kind:'compute'|'tool', permissions, author, signed, verified }>
runtime.installSkill(envelope) / runtime.uninstallSkill(skillId) / runtime.invokeSkill(skillId, input) / runtime.listSkills()
skillId = base64url( sha256( utf8(name) ‖ 0x00 ‖ utf8(author_pubkey) ) )   // see §4b(1)
```
A **separate `Map` keyed on `skillId`** — NOT the kernel's `providers` object (which single-slots on `kind`,
seed L3599, and would clobber two same-kind skills). `describe()` emits `skillId` on every installed
affordance; `invokeSkill`/`uninstallSkill` take the id (never the name), so two skills named "word-count"
from different authors coexist and are individually addressable.
`runtimeDescribe()` is extended to **union** first-party providers (one per kind, unchanged) with installed
skills (many, tagged `provenance:'installed'`, kind `compute`/`tool`). A new affordance kind `tool` joins
the validator's allowed set. **This ripples the 4-site self-description invariant** (oracle
`tools/self-description.mjs`, mirror `cli/src/identity.mjs`, `rwa doc` projection, seed `runtimeDescribe`):
- `tool` added to `AFFORDANCE_KINDS`.
- The CLI **static** projection (`rwa doc`/`ls`) reads installed-skill manifests from the in-file frozen
  skill zone and reports them (provenance `installed`, `verified` from re-checked signature) — so static and
  live agree (SD-04 style). This is a real cross-site change, scoped and tested like prior kernel work.

### 2.4 Permission grammar — two enforceable tiers
- `network:<origin-pattern>` — left-anchored per v0.7 §3.2 (exact origin / `*.` single-label / `**.`
  multi-label / `*` catch-all). Enforced by the boot CSP `connect-src` union AND the Worker fetch-bridge
  origin check (defense in depth).
- `vault:<namespace>` — exact-match string (lowercase ASCII/digits/`-`/`_`, ≤64). Enforced by the vault bridge.
Deferred (v0.9+): `fsa:`, `bus:`, `idb:` (no cheap enforcement / no use case in single-host v0.8).

### 2.5 Vault — PBKDF2 + AES-GCM, machine-local
`runtime.vault.{get,set,has,namespaces,unlock,lock,isLocked}`. PBKDF2-200k(SHA-256) → AES-256-GCM. Per-container
salt + per-entry IV in IDB `rwa_vault`. Session key cached in `sessionStorage` after unlock (never persisted);
manual lock. Worker reaches the vault **only** via the bridge. **Vault ciphertext is machine-local — it never
travels in the file** (the file carries only namespace *references* in manifests). Argon2id deferred.
Bridge error vocabulary (closed set; no mid-invoke unlock prompt — a Worker has no DOM, unlock is an explicit
settings action): `get` returns **`null`** on locked-or-missing (never throws, never hangs → clean degrade on
a 2nd machine, U4); `set` while locked throws **`vault_locked`**; namespace outside the skill's `vault:` perms
throws **`vault_namespace_denied`**; ciphertext present but AES-GCM auth fails throws **`vault_decrypt_failed`**.

### 2.6 Persistence layout
| Artifact | Lives in | Travels w/ file | Survives IDB eviction |
|---|---|---|---|
| Skill code + manifest (name, version, permissions, author pubkey, signature) | `data-rwa-frozen` skill zone in the container bytes, written on ⌘S | **Yes** | Yes |
| CSP `connect-src` union | recomputed at boot from in-file manifests, injected as `<meta>` in `<head>` | Yes (derived) | Yes (derived) |
| Vault ciphertext | IDB `rwa_vault` | **No (by design)** | No |
| Vault session key | sessionStorage | No | No |
| Source records (counts, first-seen) | IDB `rwa_sources`, **rebuilt at boot** from in-file manifests | No (rebuilt) | No |
Skill zone form: `<div data-rwa-frozen id="rwa-skills"><script type="application/rwa-skill+json">…{manifest,code,signature}…</script>…</div>`
inside INLINE_DOC, so ⌘S's `escapeForTL` (escapes `\ \` ${ </script` in that order) round-trips skill JS safely
— **byte-verified in scenario X1** (escaped backtick isn't a terminator; HTML parser sees `<\/script`; template
eval un-escapes; `dataRwaFrozenSnapshot` `outerHTML` compare round-trips equal; `JSON.parse` recovers the code).
The frozen-attribute snapshot keeps the **agent** out.

**Signature coverage (§4b-2):** the Ed25519 signature covers ONE atomic message —
`sig = sign(authorPrivKey, sha256( canonicalJSON(manifest \ signature) ‖ 0x00 ‖ utf8(code) ))` — so manifest
and code are signed *together*; you cannot swap code under a signed manifest nor weaken permissions under signed
code. The `author_pubkey` in the manifest is the identity (D). Verification re-runs **from the bytes** at every
`describe()`/boot/`rwa doc` (cheap, native Ed25519), so `verified` reflects current truth and tampering flips it
to `false`. **Unsigned ⇒ `verified:false`, permitted only for zero-capability `compute`, and it does NOT
contribute to the CSP `connect-src` union** (an unsigned skill can never widen the page's network surface).

**How the runtime edits the frozen zone (§4b-4) — install/update/uninstall.** The agent/lens path *cannot*
(snapshot equality rejects drift — correct). The **runtime** edits it by making the ⌘S commit path
**registry-aware, before `buildFile`:** rebuild `<div data-rwa-frozen id="rwa-skills">` from `installedSkills`,
swap it into the doc, then `buildFile` (the verified-safe escapeForTL round-trip). This is the *sole* writer of
the skill zone; the snapshot guard stays absolute against everything else. `uninstallSkill` deletes the registry
entry → next ⌘S rebuilds the zone without it → bytes lose the manifest → CSP tightens on next reload.

### 2.7 CSP — boot-time, derived, injected
A `skill-host` page computes its `connect-src` union from currently-installed skills' `network:` perms at boot
and injects `<meta http-equiv="Content-Security-Policy" content="… connect-src 'self' <union> …">` into `<head>`
before any skill runs. Install/uninstall updates the in-file manifest set; CSP takes effect on next reload
(honest: a boot-time property, not live-mutable — avoids mutating the frozen bootstrap, preserving Invariant 1).

## 3. Trust model (honest, with all-skills-in-Worker)
The install dialog's sentences must be *true* (Invariant 10). The exact prose:
- Boundary claim: *"A skill cannot reach a network origin or vault namespace it didn't declare."* (True: every
  skill is in a Worker; the bridge + per-call origin/namespace check + CSP are the only paths.)
- Attack-B disclosure: *"Within these limits, the skill's code decides what to do — I cannot tell whether its
  author wrote it to help you or to harm you."* (No over-promise.)
- Compound callout (E): *"⚠️ This skill can read stored credentials AND reach the network. A malicious author
  could send your secrets out. Install only if you fully trust this key."*
- Lookalike (D): *"This name closely matches '<trusted>' (edit distance N), first installed by key `…` on
  <date>. This skill's key is different. The author is identified by the key, not the name."*
- Unsigned note: *"Unsigned — I can't verify the author or that the code is unmodified."*

Capability scan: runs on the **envelope** (manifest+code) *before* persistence; regex heuristic
(`eval`/`Function`/string-`setTimeout`/computed-member); outcome is an **advisory dialog note, never an
auto-reject** (structural enforcement in the Worker is the wall; the scan informs the human).

**Current invariant violation to fix on the way in:** `tool` is *half-wired* — `AFFORDANCE_KINDS` already lists
it in both `tools/self-description.mjs` and `cli/src/identity.mjs`, but `runtimeProvide`/`runtimeDescribe`
iterate only `view/edit-surface/compute` and `KIND_PROVIDERS` has no `skill-host`. The first install would
violate the 4-site invariant until `tool` is wired through provide/describe + the static `parseSkillZone`.

Attack shapes:
- **A — permission/code mismatch:** capability scan flags `eval`/`Function`/string-`setTimeout`/dynamic indexing → dialog note. Holds.
- **B — declared perms misused:** outside any runtime's reach; purpose-prompt + "can't tell you whether it *should*" is the only, honest, defense. Unchanged from v0.7.
- **C — quiet capability expansion on update:** in-file versioned manifest → prose permission diff + re-affirmation. Holds.
- **D — plausible-source forgery:** edit-distance≤2 lookalike (Unicode confusables deferred → narrower); the **public key, not the name, is the identity**. Honest framing.
- **E — compound risk (`vault:`+`network:`):** named callout; mandatory Worker (not "recommended"). Holds. Other combos are *not hosted* in v0.8 (relabel "N/A — capability not hosted", not "defended").

## 4. Scenarios to validate the design against (the "work it along scenarios" pass)
Attack: A–E above. Usage: install compute (word-count) · install network tool (gh-stars, Worker) · update w/ expanded
perms (C) · email host to 2nd machine (portability/persistence) · uninstall → CSP tightens · unsigned import · lookalike source.
Adversarial/edge: skill code containing `</script`/backtick/`${` (escapeForTL + frozen-snapshot landmine) · two `compute`
skills (keyed-registry collision) · a Worker skill attempting `importScripts`/`indexedDB`/`fetch` to an undeclared origin ·
vault locked at invoke time · main-thread compute attempting DOM/IDB/sessionStorage reach (must be denied by scope, not just convention).
These are traced in §5 (filled by the scenario-validation pass).

## 5. Scenario walkthroughs (resolved — 17 scenarios stress-tested vs. the real seed)
Verdict: **design survives after the §2.2 reversal + the four resolved primitives.** Final handled behavior:
- **A** perm/code mismatch → scan is an advisory note; *structural* enforcement (globals removed in-Worker, per-call bridge origin/namespace check, CSP) is the wall.
- **B** declared-perms-misused → outside reach; the disclosure prose is the only, honest, defense.
- **C** update expansion → `skillId` decides update-vs-fresh; prev manifest read from the frozen zone; prose permission diff + re-affirmation; CSP recomputed at next boot.
- **D** source forgery → Levenshtein≤2 lookalike warning; key-is-identity; unsigned still lookalike-checked.
- **E** compound `vault:`+`network:` → named callout; Worker mandatory (always, for any capability skill).
- **U1** install compute → lightweight consent, now safe because compute is a *bridgeless Worker* (X5).
- **U2/U3** install+invoke network tool → full dialog, CSP union, Worker spawn, bridged fetch: `api.github.com` allowed, `evil.com` denied by **both** CSP and the bridge origin-check; terminate-after.
- **U4** email portability → code+manifest travel; vault is machine-local → `vault.get`→`null`, dialog surfaces the machine-local note; "the file is *runnable*, success may need per-device credentials."
- **U5** uninstall → runtime rebuilds the frozen zone from the registry on ⌘S (the only frozen-zone writer); CSP tightens next boot.
- **U7** `rwa doc`/`ls` → static `parseSkillZone` reports installed skills so static==live (SD-04).
- **X1** escape landmine → byte-verified safe through escapeForTL + frozen snapshot + JSON.parse.
- **X2** registry collision → separate `Map` keyed on `skillId`; same-name different-author coexist.
- **X3** Worker escape → all of importScripts/Worker/indexedDB/fetch(undeclared)/eval blocked by global-removal + CSP + bridge. **The single most important thing to build and test.**
- **X4** vault locked → `get`→`null`, `set`→`vault_locked`; no mid-invoke prompt; session-key theft eliminated by X5.
- **X5** (BLOCKER, resolved) → no main-thread skill path; compute runs in a bridgeless Worker.
- **X6** manifest forgery → frozen-snapshot blocks lens edits; signature covers `manifest‖code` atomically.

Full traces: workflow `wvuf953mw` output (`.../tasks/wvuf953mw.output`).

## 6. MVP vertical slice (corrected — proves the architecture in 7 steps)
1. `rwa new --kind skill-host` → host with an empty `<div data-rwa-frozen id="rwa-skills">` + vault/registry/CSP bootstrap.
2. **Install word-count** (compute, zero-cap, unsigned) → lightweight consent → registry → frozen-zone write on ⌘S → `rwa doc --json` reports `provenance:'installed', verified:false` (proves registry + persistence + 4-site invariant — U1/U7).
3. **Install gh-stars** (signed, `network:api.github.com`) → signature verifies → permission render → CSP `connect-src` union → frozen-zone write; registry marks `kind:'tool'` (proves §2.4/§2.6/§2.7 + `skillId` — U2/X2).
4. **Invoke gh-stars** → Worker spawn → globals removed → bridged fetch: `api.github.com` allowed, `evil.com` denied by **both** CSP and the bridge → terminate (proves the whole trust model — U3/X3, the heart of §3).
5. **Invoke word-count** in a **bridgeless Worker**; assert it *cannot* read `sessionStorage`/`indexedDB`/`document`/`fetch` (proves the X5 fix — the test that turns "honest" from a claim into a fact).
6. **Update gh-stars** to add `network:tracker.y` → prose diff + re-affirmation (proves C).
7. **Uninstall gh-stars** → ⌘S → manifest gone from bytes → reload → CSP no longer lists `api.github.com` (proves U5 + the §2.6 frozen-zone-edit mechanism). Then **email the file, open on a 2nd machine**, re-verify from bytes, invoke → vault `null`, machine-local note (proves U4 portability + X1 escape round-trip).

If those 7 pass, the architecture is proven: the install dialog is the trust anchor and every sentence it speaks is enforced by structure (Worker + bridge + CSP + signature) for **both** kinds; persistence survives email/reload byte-for-byte; identity is the key; the runtime — never the agent — is the sole editor of the frozen skill zone.

## 7. Deferred to v0.9+
bus / inter-skill messaging; Worker pool (idle/pressure/shutdown); `fsa:`/`idb:` tiers; Unicode-confusable lookalike;
`name_history`; signed-skill marketplace/distribution; installable `view`/`edit-surface` (DOM-authoring) skills; Argon2id KDF.
