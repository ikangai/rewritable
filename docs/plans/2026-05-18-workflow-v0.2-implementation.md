# Workflow v0.2 — implementation plan (adopting the UX design)

*Draft v0.1 — 2026-05-18. Maps the design in
`docs/plans/2026-05-18-workflow-ux-design.md` to concrete substrate
work. Six phases, each ships as its own commit. Supersedes
`docs/plans/2026-05-18-workflow-v1.5.md` — that plan was about
polishing v1's design; the UX design replaces v1's design entirely.*

---

## 1. What this plan implements

The UX design doc specifies:

- **Source format.** Workflow `INLINE_DOC` is a semantic
  `<article class="rwa-workflow">` containing an `<ol class="rwa-flow">`
  of `<li class="rwa-step">` cards. Each step has a `<header>` (title +
  description), a collapsible `<details>` wrapping an inert
  `<script type="text/rwa-step">`, and an `<output class="rwa-step-output">`
  slot for last-run results.
- **Step contract.** Each script defines `async function run(ctx, prev)`.
  The runner walks steps in DOM order, calls `run(ctx, prev)`, threads
  outputs as `prev` to the next step.
- **`ctx` surface.** `ctx.credentials.get(name)` reads `sessionStorage`
  with prompt-on-first-use. Future surfaces: `ctx.signal`, `ctx.log`,
  `ctx.shared`.
- **Visual gestures.** Five fixed: drag-to-reorder, ⋮-delete,
  `+`-insert-between (opens lens anchored to the gap), `<details>`
  show/hide code, Run button.
- **Lens primacy.** Everything substantive (titles, descriptions, code,
  whole-workflow restructure) goes through the lens.
- **First-prompt path.** `replace_document` for empty workflows (per
  `rwa-lens-spec.md` §4.1); `apply_edits` / `apply_dsl_plan` thereafter.
- **CORS reality.** Browser fetch is CORS-bound; only CORS-supporting
  APIs work without an OAuth proxy.

The plan implements all of this. v1's `wf-canvas` / `wf-nodes` / `wf-node`
structure is replaced wholesale.

## 2. What gets thrown away from v1

| Thrown away | Replaced by |
|---|---|
| `<article class="wf-canvas">` shell | `<article class="rwa-workflow">` |
| `<section class="wf-nodes">` container | `<ol class="rwa-flow">` |
| `<article class="wf-node">` step | `<li class="rwa-step">` |
| `<script type="text/workflow-node">` | `<script type="text/rwa-step">` |
| Statement-body wrapping in runtime | `async function run(ctx, prev)` contract |
| `data-status` attribute per step | `.running` / `.done` / `.failed` classes + `<output>` slot |
| Tolerant runtime (two-form fallback) | Single contract; agent emits `run` directly |
| Six frozen zones (wf-style / wf-run / wf-status / wf-runtime / wf-shell-open / wf-shell-close) | Two zones (`runner` and `style`); structural integrity from semantic HTML, not from frozen wrappers |
| Sentinel `<!-- wf:nodes-end -->` (v1.5 Phase 3) | `+`-between visual gesture |
| Credential `// TODO` placeholders in JS body | `ctx.credentials.get('name')` in JS body |
| Rename `workflow` → `pipeline` (v1.5 Phase 5) | UX design keeps `workflow` — linear in v0.1, branches when demanded |

## 3. What survives from v1

| Kept | Why |
|---|---|
| Substrate `computeShape` fix (commit `1190307`) | Inline `<script>` still counts; non-executable type exemption still needed. The `type="text/rwa-step"` MIME is non-executable; existing rule covers it. |
| `PRODUCT_KIND` substitution (audit R1) | Selects `SYSTEM_PROMPTS.workflow` at module-load time. |
| `LENS_PLACEHOLDER` + `LEGACY_PAL_PLACEHOLDER` hoisted consts | Lens-copy single source of truth across three render sites. |
| `LENS_CLICK_TO_ANCHOR = false` for workflow kind | UX design agrees: every step is implicitly anchorable through the lens; click-to-anchor isn't useful before there are steps. |
| The R9-minimal `KIND_TABLE` machinery | Workflow is still one kind among several substitution regions; the machinery is the same. |
| `LENS_PLACEHOLDER` value for workflow | UX design's *"describe what you want this workflow to do"* replaces v1's *"add an item, or describe a stage move"*. |

## 4. Phases

### Phase 1 — Stub + SYSTEM_PROMPT replacement

**Files touched:** `cli/src/seed.mjs`, `seeds/rewritable.html`,
references regenerated.

**Substance:**

- `KIND_TABLE.workflow` gets a new `body` (the UX design's empty-skeleton:
  `<article class="rwa-workflow">` with a placeholder paragraph + the
  frozen runner script) and new `lensPlaceholder` / `palPlaceholder`
  values per the UX design.
- `PRODUCT_HEADER` for workflow becomes the UX design's framing — names
  the linear-pipeline-now / branches-later trajectory, the CORS
  constraint, the credential surface.
- `SYSTEM_PROMPTS.workflow` is rewritten end-to-end per the UX design's
  §"What `rwa new --kind workflow` produces":
  - The workflow `INLINE_DOC` structure (`<ol>` of `<li class="rwa-step">`).
  - The step contract (`async function run(ctx, prev) { ... }`).
  - The `ctx.credentials.get('name')` pattern.
  - The frozen runner — never edit.
  - First-prompt → `replace_document`; subsequent edits →
    `apply_edits` / `apply_dsl_plan`.
  - CORS reality (only CORS-supporting APIs work without a proxy).
  - `data-rwa-id` discipline (preserved verbatim per the existing
    substrate convention; the substrate auto-injects on `<li>` because
    `LI` is in `ANCHORABLE_TAGS`).
  - Inherits the shared `SYSTEM_PROMPT_RULES`.

**Dependencies:** none.

**Verification:** `rwa new --kind workflow /tmp/test.html` produces the
expected stub. Open in browser; lens placeholder reads right; Run button
visible; the placeholder paragraph reads *"Describe what you want this
workflow to do…"*. No actual model call yet.

**Size:** half a day.

### Phase 2 — CSS for the workflow stack

**Files touched:** `cli/src/seed.mjs` (the workflow body's frozen
`<style>` block).

**Substance:** vertical stack of step cards. Per the UX design:

- `.rwa-workflow` — max-width container, padding.
- `.rwa-flow` — vertical `<ol>` with gap, no default list bullets
  (`list-style: none`).
- `.rwa-step` — card with rounded border, padding, hover affordance
  for the drag handle.
- `.rwa-step > header` — title + description; `<h3>` styled for
  hierarchy, `<p>` lighter weight.
- `.rwa-step > details` — collapsed by default; `<summary>` styled as
  a small interactive control.
- `.rwa-step > details > script` — actually hidden; the visible
  `<details>` shows the code only when expanded. (`<script>` is
  always invisible by default; styling the `<details>` summary is
  what matters.)
- `.rwa-step-output` — monospace, smaller font, scrollable if long;
  hidden when empty.
- `.rwa-step.running` — left border accent (blue), pulse animation
  optional.
- `.rwa-step.done` — left border accent (green) + checkmark.
- `.rwa-step.failed` — left border accent (red) + ✗ + output rendered
  as error styling.
- `.rwa-step + .rwa-step` — gap between cards; if visual gestures land
  in Phase 4, an `:hover` `+`-between affordance.
- `.rwa-workflow-footer` — Run button + status area, sticky bottom or
  inline; per UX design "one Run button + status region."
- `.rwa-run` — primary button styling (matches the substrate's `--gray-900`
  primary-action color).

**Dependencies:** Phase 1 (stub structure must exist for the CSS to bind).

**Verification:** open the empty workflow file in a browser; visual
matches the UX design's intent (clean card layout, collapsible code,
Run button prominent). No model interaction yet.

**Size:** 1 day.

### Phase 3 — Runner script

**Files touched:** `cli/src/seed.mjs` (the workflow body's frozen
runner `<script>` block).

**Substance:** the ~30-LOC runner from the UX design's source-format
example. Walks `li.rwa-step script[type="text/rwa-step"]` in DOM
order, compiles each into an async function by appending
`return run(ctx, prev);` and wrapping in `new Function(...)`, invokes
in sequence threading `prev`, writes `JSON.stringify(prev, null, 2)`
into the step's `<output>` slot, sets `.running` / `.done` / `.failed`
classes accordingly, stops the chain on error and renders the error
message into the failing step's `<output>`.

`ctx` carries `credentials.get(name)` (sessionStorage with
prompt-on-first-use, per UX design §Credentials). Future surfaces
(`signal`, `log`, `shared`) are noted in a comment but not implemented.

The runner is wrapped in `<!-- rwa:frozen:begin runner -->` /
`<!-- rwa:frozen:end runner -->` so the agent can't accidentally
mangle it.

**Dependencies:** Phase 1 (the runner expects the `.rwa-workflow`
structure).

**Verification:**

1. Open the empty workflow file in a browser. Click Run. Expect
   status: "no steps to run" or similar. No crash.
2. Manually inject a `<li class="rwa-step">` with a known-good
   script body (e.g. `async function run(ctx, prev) { return 'hello'; }`).
   Click Run. Expect: step gets `.done` class, output slot shows
   `"hello"`.
3. Inject two steps where the second uses `prev`. Verify chaining.
4. Inject a step that throws. Verify `.failed` class, error in output,
   chain stops.

**Size:** half a day.

### Phase 4 — Visual gestures (the small fixed set)

**Files touched:** `cli/src/seed.mjs` (the workflow body's frozen
runner script — extended with event handlers and synthetic
`apply_edits` envelope construction).

**Substance:** Five gestures per the UX design §"Visual manipulation":

| Gesture | Mechanism |
|---|---|
| Show / hide code | Native `<details>` toggle. **Free** — no JS needed. |
| Run | The button + the chain walker from Phase 3. **Already in Phase 3.** |
| Drag-to-reorder steps | `dragstart` / `dragover` / `drop` on each `<li>`. On drop, synthesize an `apply_edits` envelope that swaps the two `<li>` source ranges; call `window.modify` or `window.synthesizeAndCommit` to commit through the existing audit pathway. |
| Delete step (⋮ menu) | Each `<li>` carries a small button (CSS-styled "⋮" or "×"). On click, synthesize an `apply_edits` with `find = step source, replace = ""`; commit. |
| Insert between (`+` button) | Each gap between `<li>`s reveals a `+` button on hover. On click, open the lens with the cursor anchored to the gap; the user types what they want; the agent emits an `apply_edits` with the right insertion point. |

The drag-reorder and delete gestures synthesize **edit envelopes**, not
runtime mutations. They commit through `applyEdits` (or
`synthesizeAndCommit`) so they go through the substrate's audit log,
shape-check, frozen-zone enforcement, and undo stack. ⌘Z works.

The insert-between gesture is more interesting — it needs to anchor
the lens to a specific position. Likely shape: the gesture sets
`lensState.anchor` to a virtual entry pointing at the gap (between
two `<li>`s), then opens the lens. The user types; the agent's
output replaces the anchor with `node + anchor` verbatim, landing the
new step in the gap. Re-uses the existing anchored-state lens
machinery.

If insert-between is hard to get right in Phase 4, **ship without it**
and defer to a Phase 4.5. The lens always works as a fallback ("add
a step after the second one that ..."). The `+` gesture is UX polish,
not a load-bearing feature for v0.2.

**Dependencies:** Phases 1–3.

**Verification:**

1. Drag a step to reorder. Confirm: DOM updates, `rwa_hist` records the
   edit, ⌘Z restores. Run after reorder produces the new chain order.
2. Click ⋮ → delete a step. Confirm: removed, audit logged, ⌘Z restores.
3. Click `+` between two steps; lens opens anchored. Type "add a step
   that returns 42". Confirm: new step lands in the gap with code
   that returns 42; Run threads it through.
4. Click `<summary>` of a step's `<details>`. Code expands/collapses
   visually. No commit (it's a native HTML interaction).

**Size:** 2 days for all five gestures. If we ship without
insert-between, 1 day.

### Phase 5 — Conformance scenarios

**Files touched:** `benchmark/scenarios/conformance/*.mjs` (new
scenarios).

**Substance:** four new scenarios:

- **`SHAPE-01`** (substrate-level, regression for commit `1190307`):
  `applyEdits` accepts an edit that adds a `<script type="text/rwa-step">`
  to a doc with one existing executable script. Shape unchanged.
  Documents the script-type exemption rule in code.
- **`SHAPE-02`** (substrate-level, negative): `applyEdits` *rejects*
  an edit that adds a `<script>` (no type, no special attrs).
  Returns `structural_shape_changed`. Verifies the original rule
  still applies — we haven't accidentally exempted everything.
- **`WORKFLOW-01`** (workflow product end-to-end): a stub matching
  `KIND_WORKFLOW_BODY` (post-Phase 1 rewrite) + an `apply_edits`
  envelope that inserts a `<li class="rwa-step">` into the empty
  workflow's `<ol class="rwa-flow">`. Verify: step lands, frozen
  runner survives, shape unchanged.
- **`WORKFLOW-02`** (workflow product, two-step): apply a sequence
  of two `apply_edits` envelopes that add two steps in order. Verify
  ordering, both steps render, `data-rwa-id` auto-injected on each
  `<li>` (because `LI` is in `ANCHORABLE_TAGS`), audit log records
  both.

These don't require an LLM — they're scripted edit envelopes against
the substrate.

**Dependencies:** Phases 1–3.

**Verification:** all four scenarios pass; existing 42 still pass;
e2e suite (291) still passes.

**Size:** 1 day.

### Phase 6 — End-to-end model verification

**Files touched:** none code-wise; produces a smoke-test report.

**Substance:** scripted manual testing via `chrome-devtools-mcp`,
same methodology as v1. The UX design's "morning invoice processor"
prompt is the canonical case; smaller cases for each gesture.

For each prompt + gesture, an assertion. The prompts:

1. **Empty-workflow generation.** `/Each morning, fetch unread emails
   tagged 'Invoices', extract PDF attachments, parse them, and append
   to a CSV file.` Expect: `replace_document` envelope; agent fills
   out the full structure with 4–5 steps; each step has a real
   `run(ctx, prev)` function; credentials are `ctx.credentials.get('gmail')`
   shape; CORS-reality warning in the agent's response (or in the
   workflow's preamble paragraph).
2. **Add a step.** `/add a step at the end that emails me a summary
   when done`. Expect: new step lands at the bottom; uses
   `ctx.credentials.get('email')`.
3. **Edit a step.** `/edit step 2 to also extract image attachments`.
   Expect: same step (same `data-rwa-id`), updated code, updated
   description.
4. **Remove a step.** `/remove the CSV append step`. Expect: that
   step gone, others intact.
5. **Reorder.** Drag step 3 above step 2. Expect: order flipped in
   DOM and on Run.
6. **Run a simple workflow.** A workflow with one step that returns
   `"hello"`; Run; expect `<output>` shows `"hello"`, `.done` class.
7. **Run a CORS-friendly workflow.** A workflow that fetches
   `https://api.github.com/repos/anthropics/anthropic-sdk-python/issues?per_page=3`
   and returns titles. Expect: actually runs, output shows the
   array.
8. **Run with credentials.** A workflow with a step that calls
   `ctx.credentials.get('test')`. First Run: prompt appears for
   `test`; user types value; output reflects it. Second Run (same
   session): no prompt; uses cached.
9. **⌘S + reload.** Build a 2-step workflow; commit; reload; Run.
   Expect: runtime re-binds, Run works, steps intact.

For each failure, document the failure mode. Some are model-quality
issues; others may reveal substrate or runtime bugs.

**Dependencies:** Phases 1–5.

**Verification:** the manual tests are the verification, plus a written
report of what worked / what didn't / what needs Phase 7 (v0.3 polish).

**Size:** 1 day plus whatever fixes the failure modes reveal.

## 5. Open decisions (resolve before / during execution)

1. **Visual gesture scope for v0.2.** Five gestures specified. If time
   presses, ship without insert-between (the `+`-between gap UX) and
   defer to v0.3. The lens always works as a fallback. **Default: ship
   all five.** Reconsider if Phase 4 takes longer than 2 days.
2. **Code shown or hidden by default.** UX design open question
   §10.2. Default in Phase 1: collapsed (`<details>` without `open`
   attribute). Workflow files are self-documenting at the *title*
   level; the user expands to read code.
3. **Where last-run output persists.** UX design open question §10.2.
   Default in Phase 3: rendered into the step's `<output>` inside
   `INLINE_DOC` (so the agent and the next reload see the last
   result), but **NOT** committed via ⌘S unless the user explicitly
   re-commits after running. The simpler-thinking model.
4. **`data-verb`.** UX design open question §10.2 says skip in v0.1.
   **Skip.**

## 8. What this plan doesn't do

- **No skill layer.** Per UX design and per audit R7 deferral.
- **No vault encryption.** sessionStorage-prompted credentials only.
- **No Worker isolation.** Inline scripts run in the document context.
  The trust gesture is workflow review at creation, not skill install.
- **No registry / discovery / marketplace.** Workflows are `.html`
  files; copy, fork, edit. The existing `/publish` flow works
  unchanged.
- **No DAG / branches / parallel.** Source format accommodates them
  via nested `<ol>` (UX design §"Branches"), but the runner ships
  linear-only.
- **No scheduling.** No cron. The user clicks Run.
- **No retry / resume.** Failed runs stop. Re-run starts from the top.
  Future work could checkpoint outputs in `runtime.shared.*` for
  resume-from-failure.

All of these are explicitly deferred in the UX design. They're noted
here only to make the v0.2 scope unambiguous.

## 9. After v0.2

If v0.2 ships clean, the natural next questions:

- Do real workflows surface real demand for branches / parallel /
  resume? If yes, `rwa-graph/1` spec work begins.
- Do real workflows surface CORS pain that warrants a proxy story?
  (Probably yes for anything Gmail / Outlook / consumer SaaS-adjacent.
  Out of scope for v0.2; design pass when it bites.)
- Do real workflows surface credential pain that pulls toward the
  skill-layer vault? If yes, the deferred R7 plan
  (`docs/plans/2026-05-18-action-layer-implementation.md`) is ready
  when the signal is real.

v0.2 stops at "the workflow product is structurally sound, lens-
editable, visually navigable, and tested end-to-end." Anything further
is a separate decision against actual demand.
