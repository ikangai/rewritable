# Workflow v1.5 — substrate hardening + structural soundness

*Draft v0.1 — 2026-05-18. Six phases addressing the architectural gaps
identified in the post-v1 self-review (see the conversation that
produced commits 7eb6998 / 1190307 / e091544 and the subsequent review).
Sized for focused work; ordering reflects dependencies. Each phase ships
as its own commit.*

---

## 1. Why this exists

Workflow v1 shipped a working demo (canvas + node cards + frozen runtime
helper + the `--kind workflow` CLI). End-to-end testing surfaced both a
real substrate bug (`computeShape` counted non-executable scripts toward
the doc's "shape" → rejected every agent node insertion) and several
gaps the v1 commits papered over rather than fixed structurally:

- Frozen zones protect the runtime infrastructure but not the workflow's
  *structural* integrity. The agent can scatter nodes outside
  `<section class="wf-nodes">`, restructure the canvas wrapper, etc.
- The `computeShape` fix exempts scripts by MIME type only. If the model
  forgets `type="text/workflow-node"`, the bug returns silently.
- Zero automated test coverage for the workflow product. Conformance and
  e2e are all document-product.
- The product is named `workflow` but is structurally a linear pipeline;
  no branching, no parallel paths, no edges. The name oversells.
- Multi-node insertion ordering is unreliable — the model sometimes
  inserts before existing nodes despite the prompt.
- Operations beyond "add a trivial node" are unverified — editing,
  removing, reordering, real fetch work, ⌘S + reload survival.

This plan addresses each gap in turn. The goal is a workflow product
that earns "the file is the workflow" — solid enough to learn from
in real use, with the substrate honest about what it enforces.

## 2. Scope

**In scope:**
- Substrate `computeShape` hardening (a second signal beyond MIME type).
- Frozen-zone rework so the workflow shell is structurally protected.
- A sentinel-comment insertion anchor so multi-node insertion is
  deterministic.
- Conformance test coverage — both the substrate rule and the workflow
  product.
- Rename `--kind workflow` → `--kind pipeline` to match what v1
  actually is. Reserve `workflow` for the future graph-layer product.
- Verification pass: edit, remove, reorder nodes; nodes that do real
  work (fetch); commit + reload survival.

**Out of scope:**
- Action layer / vault / skill library — see
  `docs/plans/2026-05-18-action-layer-implementation.md`. Parked.
- Worker isolation for inline node scripts — same plan, deferred.
- CSP / `new Function` interaction — surfaces when hosted shares
  start enforcing CSP; deferred to v2.
- Per-node timeout, branch / parallel execution — pipeline semantics
  only in v1.5.
- Graph-layer workflows (`rwa-graph/1` spec) — separate doc when
  there's product pull for them.

## 3. Phases

### Phase 1 — Substrate: `computeShape` data-node-id signal (audit follow-up to commit 1190307)

**Problem.** The current `computeShape` (seeds/rewritable.html
~line 2536) exempts scripts by MIME type only:

```js
const EXEC_TYPES = new Set(['', 'text/javascript', 'application/javascript', 'module']);
```

If the model emits `<script>` with no type, the empty-string type
matches `EXEC_TYPES` and the script counts as executable → shape
changes on insert → `structural_shape_changed`. Model variance
defeats the fix.

**Fix.** Second signal: any `<script>` with `data-node-id` attribute
is workflow data regardless of type:

```js
const scripts = Array.from(parsedDoc.querySelectorAll('script'))
  .filter(s => {
    if (s.hasAttribute('data-node-id')) return false;   // workflow data
    const t = (s.getAttribute('type') || '').toLowerCase();
    return EXEC_TYPES.has(t);
  });
```

Either signal exempts the script. The SYSTEM_PROMPT emphasizes both
(`type="text/workflow-node"` AND `data-node-id="…"`); the agent has
two chances to get it right.

**Dependencies:** none. Smallest change in the plan; ships first.

**Verification:** caught by Phase 4's new conformance scenarios. No
behavior change for any executable-script doc.

**Size:** 1 hour for the seed change + regenerate + run existing tests.

### Phase 2 — Workflow shell: structural frozen zones

**Problem.** Four frozen zones today (`wf-style`, `wf-run`,
`wf-status`, `wf-runtime`) protect the runtime infrastructure. The
*structural* shell (`<article class="wf-canvas">`, `<header>`,
`<section class="wf-nodes">` opening + closing tags) is unprotected.
Agent edits can:

- Move `<article class="wf-canvas">` somewhere weird.
- Remove `<header>`.
- Restructure or rename `<section class="wf-nodes">`.
- Add nodes outside `.wf-nodes` (observed in v1 testing — model did
  this on the second prompt without prompting changes).

The runtime helper's `querySelector('.wf-nodes')` and
`querySelector('.wf-run')` assume the shell is intact; if the agent
breaks it, things stop working in confusing ways.

**Fix.** Two new frozen zones wrap the structural shell. The
editable region is exactly the *inside* of `<section class="wf-nodes">`:

```html
<!-- rwa:frozen:begin wf-shell-open -->
<article class="wf-canvas">
<header>
<h1>Untitled workflow</h1>
<!-- existing wf-run frozen zone here -->
</header>
<!-- existing wf-status frozen zone here -->
<section class="wf-nodes">
<!-- rwa:frozen:end wf-shell-open -->

  [editable region — node cards + wf-empty placeholder]

<!-- rwa:frozen:begin wf-shell-close -->
</section>
</article>
<!-- rwa:frozen:end wf-shell-close -->
```

Six frozen zones total. The runtime infrastructure + the structural
shell are both protected; only the node list inside `.wf-nodes` is
editable by the agent.

**Trade-off.** The `<h1>` is now inside `wf-shell-open` — workflow
rename via lens is no longer possible. Acceptable for v1.5: the
filename → `<title>` substitution from CLI's `titleFromBasename` still
gives a meaningful browser-tab title. The in-document `<h1>` stays
"Untitled workflow" unless edited externally.

If the rename gesture matters later, the alternative is three smaller
frozen zones (`wf-shell-open-a` / `<h1>` editable / `wf-shell-open-b`),
which adds ~2× the marker count but preserves the rename path. Defer.

**SYSTEM_PROMPT update.** Replace the current list of frozen zones
with the new six: `wf-style`, `wf-run`, `wf-status`, `wf-runtime`,
`wf-shell-open`, `wf-shell-close`. Name the editable region explicitly:
*"Your edits target only the region inside `<section class="wf-nodes">`,
between the `wf-shell-open` and `wf-shell-close` frozen markers.
Everything else is structural infrastructure and is off-limits."*

**Dependencies:** none. Independent of Phase 1.

**Verification:** Phase 4's `PIPELINE-01` scenario.

**Size:** half a day.

### Phase 3 — Sentinel insertion anchor

**Problem.** SYSTEM_PROMPT v1 says "insert immediately before the
`<p class="wf-empty">` placeholder." Models sometimes obey, sometimes
anchor on `<section class="wf-nodes">` instead and place nodes at the
top. In testing, a second node was inserted *before* the first one,
causing the first node to receive `null` instead of the previous
node's output.

**Fix.** A non-`rwa:` sentinel comment inside the editable region.
The agent always anchors on it; new nodes always land in the same
position:

```html
<!-- rwa:frozen:end wf-shell-open -->

<!-- wf:nodes-end -->
<p class="wf-empty">No nodes yet…</p>

<!-- rwa:frozen:begin wf-shell-close -->
```

SYSTEM_PROMPT update:

> *"For inserting any new node, the apply_edits anchor is the literal
> string `<!-- wf:nodes-end -->`. Replace it with your new
> `<article class="wf-node">…</article>\n<!-- wf:nodes-end -->`. The
> sentinel stays in place; nodes accumulate above it in insertion
> order."*

`wf:` is not a reserved prefix (only `rwa:` is), so the sentinel is
the agent's anchor — `apply_edits` does a literal substring match,
so the agent doesn't need to "produce" the sentinel; it copies it
from the doc verbatim and reproduces it in the replace string.

**Dependencies:** Phase 2 (the sentinel sits inside the editable
region defined by `wf-shell-open` / `wf-shell-close`).

**Verification:** `PIPELINE-01` scenario in Phase 4.

**Size:** half a day.

### Phase 4 — Conformance test coverage (×4 new scenarios)

**Problem.** Zero automated coverage for the workflow product. The
`computeShape` change (Phase 1 + v1 commit 1190307) has no test that
fails when the rule reverts. Future regressions will land silently.

**Plan.** Four new scenarios under
`benchmark/scenarios/conformance/`:

- **`SHAPE-01`** (substrate-level): `applyEdits` accepts an edit
  that adds a `<script type="text/workflow-node">` to a doc that
  already has one executable script. Shape unchanged.
- **`SHAPE-02`** (substrate-level): `applyEdits` accepts an edit
  that adds a `<script data-node-id="abc">` without a `type=`
  attribute. Shape unchanged. Verifies Phase 1's second signal.
- **`SHAPE-03`** (substrate-level, negative): `applyEdits` *rejects*
  an edit that adds a `<script>` (no type, no `data-node-id`).
  Returns `structural_shape_changed`. Verifies the original rule
  still applies — we haven't accidentally exempted everything.
- **`PIPELINE-01`** (workflow product end-to-end): a stub matching
  `KIND_PIPELINE_BODY` (post-Phase 5 rename) plus an `apply_edits`
  envelope that anchors on `<!-- wf:nodes-end -->` and inserts a
  node. Verify (a) the node lands in the right place, (b) the
  sentinel survives verbatim, (c) the `wf-empty` placeholder is
  unmodified, (d) all six frozen zones are intact post-edit.

Each scenario is small (the conformance harness is mature; existing
scenarios under `benchmark/scenarios/conformance/` are good
templates).

**Dependencies:** Phases 1, 2, 3.

**Verification:** the four scenarios are the verification.

**Size:** 1 day.

### Phase 5 — Rename `--kind workflow` → `--kind pipeline`

**Problem.** v1 is structurally a linear pipeline (sequence of
nodes, output feeds next as `input`, no branching, no edges, no
parallel paths). The name `workflow` oversells — sets the
expectation that `--kind workflow` is what users get out of n8n /
Yahoo Pipes / Zapier-shaped tools. Reserve `workflow` for the
future graph-layer product when `rwa-graph/1` lands.

**Plan.**

| File | Change |
|---|---|
| `cli/src/seed.mjs` | `KIND_TABLE.workflow` → `KIND_TABLE.pipeline`. `KIND_WORKFLOW_*` consts → `KIND_PIPELINE_*`. |
| `cli/bin/rwa.mjs` | `KNOWN_KINDS = ['document', 'pipeline']`. Help text. |
| `cli/README.md` | Flag table row, the description under `rwa new`. |
| `seeds/rewritable.html` | `SYSTEM_PROMPTS.workflow` → `SYSTEM_PROMPTS.pipeline`. Update any prose that mentions "workflow product." |
| `CLAUDE.md` | CLI-conventions bullet about known kinds. |
| `docs/specs/rwa-product-types.md` | Rename the §2 workflow entry to pipeline; add a forward-looking note about `--kind workflow` being reserved for the future graph-layer product. |

**Backward compatibility.** None. Any existing `*-workflow.html`
files on disk have `PRODUCT_KIND = 'workflow'` baked into their
bootstrap. After the rename, `SYSTEM_PROMPTS.workflow` is gone —
those files fall back to `SYSTEM_PROMPTS.document` (the `||` in the
resolver), which gives them the wrong system prompt.

Two options:

- **(a) Just rename.** v1 was explicitly a demo; existing files are
  scratch artifacts; users regenerate. Cheapest now, expensive later
  if anyone ships a workflow file in the wild.
- **(b) Keep `workflow` as an alias.** `SYSTEM_PROMPTS.workflow =
  SYSTEM_PROMPTS.pipeline`. Soft deprecation. Mark the alias in
  comments; remove in v2.

**Default**: (a). v1 was a demo, the rename is cheap now, and the
alias would muddy the registry. If anyone ships a workflow file in
production scope between v1 and v1.5, switch to (b) before this
commit.

**Dependencies:** Phases 1, 2, 3 (so the rename captures the
post-rework structural shell + sentinel + computeShape rule
together).

**Verification:** Phase 4's `PIPELINE-01` scenario uses the
post-rename name. Manual `rwa new --kind pipeline` smoke test.

**Size:** 1 day.

### Phase 6 — Verification of operations beyond "add a single trivial node"

**Problem.** v1 was claimed end-to-end but only verified for `return
"X";` style nodes. Edit / remove / reorder operations are unverified.
Nodes that do real work (`fetch`, `runtime.modify` from inside a
node, `runtime.db.put`) are unverified. ⌘S + reload survival is
unverified.

**Plan.** Scripted manual testing via chrome-devtools-mcp, same
methodology as v1 end-to-end. For each operation, a prompt + assertion
+ verification:

1. **Edit a node.** Sequence: `/add a Greet node that returns
   "hello"` → `/edit the Greet node to return "goodbye" instead`.
   Assert: same `data-node-id`, JS body changed, no new node added,
   ⌘Z restores.
2. **Remove a node.** Sequence: add A, add B, `/remove the first
   node`. Assert: only B remains, placeholder still hidden (CSS),
   sentinel intact.
3. **Reorder a node.** Sequence: add A, add B, `/move A after B`.
   Assert: DOM order is B then A.
4. **Real-work node (fetch).** Sequence: `/add a node that fetches
   https://api.github.com/repos/anthropics/anthropic-sdk-python/issues?per_page=3
   and returns the array of issue titles`. Assert: Run produces
   `lastResult` that's an array of 3 strings (the actual issue
   titles); no errors.
5. **Real-work node (runtime.modify).** Sequence: add a node that
   calls `runtime.modify("change h1 to 'Done'")` against the
   workflow file itself. *Note: this is novel — a workflow that
   modifies its own document via the substrate's modify loop.
   Expect interesting failure modes; document them.*
6. **⌘S + reload.** Sequence: add 2 nodes, ⌘S (or download), close
   tab, reopen file. Assert: nodes visible, Run works, runtime
   helper re-binds.

For each failure, document the failure mode. Some will be model-quality
issues (re-prompt + retry); others may reveal real substrate or runtime
bugs to fix in v1.5 or queue for v1.6.

**Dependencies:** Phases 1–5.

**Verification:** the manual tests are the verification, plus any
new failures that need queued fixes.

**Size:** 1 day, plus whatever fixes the failure modes reveal.

## 4. Open questions

1. **Phase 5 — `workflow` rename: (a) just rename vs. (b) alias-with-
   deprecation?** Default: (a). Asks for confirmation before Phase 5
   starts.
2. **Phase 2 — `<h1>` renamable via lens, or not?** Default: not
   (inside the `wf-shell-open` frozen zone). If rename matters, switch
   to three-zone variant before Phase 2 starts.
3. **Phase 6 — node-calls-runtime.modify case.** A self-modifying
   workflow is interesting and unprecedented in v1. The substrate's
   `modifyMutex` will refuse a reentrant call. Either the test
   reveals a meaningful pattern (node defers modify via setTimeout
   to escape the mutex) or it documents that self-modification
   from inside a workflow node is not supported in v1.5. Decision
   depends on what the test surfaces.

## 5. Sequence and dependencies

```
Phase 1 (computeShape data-node-id) ───┐
                                       ↓
Phase 2 (structural frozen zones) ──→ Phase 3 (sentinel anchor) ──→ Phase 4 (×4 conformance) ──→ Phase 5 (rename) ──→ Phase 6 (verify)
```

Phases 1 and 2 are independent; Phase 1 is smaller and ships first
to keep changes well-scoped. Phase 3 depends on Phase 2 (sentinel
sits inside the post-rework editable region). Phase 4 needs all
three substrate changes in place. Phase 5 is a clean rename pass
over the post-Phase-4 state. Phase 6 verifies everything.

with workflow-as-pipeline as a stable v1.5 product.

## 7. After v1.5

If v1.5 ships clean, the natural next questions:

- Does the pipeline product earn real usage? (Watch what users
  actually build with `--kind pipeline`.)
- If users want branching / parallelism / per-node errors-to-branch,
  that's `rwa-graph/1` work. The v1.5 pipeline doesn't try to be it.
- If users want skills / credentials / Worker isolation, the deferred
  R7 plan (`docs/plans/2026-05-18-action-layer-implementation.md`) is
  ready when there's a real signal.

v1.5 stops at "the pipeline product is structurally sound and tested."
Anything further is a separate decision against actual demand.
