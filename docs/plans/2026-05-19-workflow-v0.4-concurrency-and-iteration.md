# Workflow v0.4 — concurrency & iteration

**Date:** 2026-05-19
**Goal:** add two composable primitives to the workflow product —
**parallel-as-columns** (`<table class="rwa-parallel">`) and
**foreach loops** (`<li class="rwa-foreach">` with nested
`<ol class="rwa-flow">`). Both compose freely with each other and
with linear steps; the linear `<ol>` remains the default.
**Pre-req:** v0.3 (pin / dirty / test-step) shipped — the per-step
affordances inherit to the new shapes naturally.

## TL;DR

Three primitives, recursive composition:

| Shape | HTML | Meaning |
|---|---|---|
| **Linear** | `<ol class="rwa-flow"><li class="rwa-step">…</li>…</ol>` | sequential pipeline; `prev` threads forward (v0.2, unchanged) |
| **Foreach** | `<li class="rwa-step rwa-foreach"><ol class="rwa-flow">…</ol></li>` | inner `<ol>` runs once per item in upstream array |
| **Parallel** | `<table class="rwa-parallel"><tr><td class="rwa-step" data-rwa-label="...">…</td>…</tr></table>` | one row of N cells, each gets same `prev`, all run via `Promise.all` |

The cards / tables nest. "For each repo, in parallel fetch issues
and PRs" reads top-to-bottom as one outer foreach card containing one
inner parallel table. That structure is the spec.

## Non-goals (deferred to v0.5+)

- **Multi-row parallel tables** (synchronized parallel pipelines —
  each column its own internal pipeline that meets others at row
  boundaries). Real use cases exist but the mental model is
  noticeably heavier; defer until v0.4 ships and we see who asks.
- **Per-cell failure containment** (`Promise.allSettled` instead of
  `Promise.all`, opt-in per cell via `data-allow-failure`). Default
  in v0.4: fail-fast. v0.5 can add the escape hatch.
- **Dynamic parallelism** (spawn N parallel branches based on a
  runtime value). Use foreach instead — same shape from above.
- **Inter-cell communication within a parallel block** (sibling
  cells reading each other's outputs). They share only the upstream
  `prev`; siblings are isolated by design.

## Data flow contracts

### Linear (v0.2 — restated for completeness)

Step N receives `prev` = Step N−1's return value. Step 0 receives
`prev = undefined`. Pipeline output = last step's return.

### Foreach

```html
<li class="rwa-step rwa-foreach" data-rwa-id="...">
  <header><h3>For each invoice</h3><p>...</p></header>
  <ol class="rwa-flow">
    <li class="rwa-step">...</li>
    <li class="rwa-step">...</li>
  </ol>
  <output class="rwa-step-output"></output>
</li>
```

- **Upstream contract:** the step before the foreach must return
  an array. Non-array → runtime error
  `foreach_upstream_not_array`.
- **Each iteration:** the inner `<ol>` executes top-to-bottom with
  `prev = currentItem` for the *first* inner step. `ctx.iter` is
  populated as `{ index, item, total }` for *every* step in the
  inner pipeline (it's a property of the iteration, not the depth).
  Within an iteration, `prev` threads forward exactly as in linear.
- **Output:** the foreach card's own output is an array of the
  inner pipeline's per-iteration final outputs (one element per
  upstream item). Downstream sees that array as `prev`.
- **Empty array upstream:** zero iterations, output `[]`. Not an
  error.

### Parallel

```html
<table class="rwa-parallel" data-rwa-id="...">
  <tbody>
    <tr>
      <td class="rwa-step" data-rwa-label="gmail" data-rwa-id="...">
        <header><h3>Fetch Gmail</h3></header>
        <details><summary>Code</summary><script type="text/rwa-step">…</script></details>
        <output class="rwa-step-output"></output>
      </td>
      <td class="rwa-step" data-rwa-label="slack" data-rwa-id="...">…</td>
      <td class="rwa-step" data-rwa-label="linear" data-rwa-id="...">…</td>
    </tr>
  </tbody>
</table>
```

- **Upstream contract:** any value. All cells share the *same*
  `prev`.
- **Each cell:** executes independently with `prev` and a normal
  `ctx`. Cells do not see each other.
- **Concurrency:** all cells launched together via `Promise.all`.
- **Output:** an object keyed by `data-rwa-label`, values =
  each cell's return. **Label is required for v0.4** —
  positional indexing on a `prev` object is the kind of footgun
  that bites non-programmers. Validation: each cell must carry
  `data-rwa-label`, all labels must be unique within the row,
  labels must match `[a-z][a-z0-9_]{0,31}` (lowercase, snake_case,
  safe to use as a JS property without quoting). Violations →
  runtime error `parallel_label_invalid` (caught at boot-scan time
  so the user sees it before Run).
- **Error semantics:** one cell rejects → `Promise.all` rejects →
  the whole pipeline halts on that step. The failing cell shows
  `.error` class with the message; sibling cells finish their
  work but their outputs aren't piped downstream. (v0.5 adds
  per-cell `data-allow-failure="true"` to switch a cell to
  `Promise.allSettled`-style behavior.)

### Composition examples

The shapes nest freely. The runner's tree-walker doesn't care which
contained which; it just executes the right primitive for each node.

- **Parallel fetches inside a loop:** `<li rwa-foreach><ol>` →
  inside the inner `<ol>`, a `<table class="rwa-parallel">` row.
- **Loop inside a parallel cell:** `<td class="rwa-step">` whose
  body is itself a `<li rwa-foreach>`. Yes, this works — the cell's
  content can be a nested workflow fragment. (Probably rare;
  document as supported but don't optimize for it.)

## Per-step affordances (v0.3 carryover)

Every node that is a "step" — `<li class="rwa-step">` (linear or
foreach) or `<td class="rwa-step">` (parallel) — inherits the v0.3
affordances:

- **Pin** (`data-pinned-output`) — short-circuits the cell's
  `run()`. For a foreach card pinning the array is the right
  semantics (skip the whole loop, return the pinned array).
- **Last-output cache** (`data-last-output`) — populated on
  successful run for the test-step button to use.
- **Dirtiness** (`data-last-run-hash`) — invalidates on script
  body change. For container nodes (foreach, parallel table), the
  hash includes a structural fingerprint of the contained nodes,
  so editing any inner step marks the container `.stale` too.
- **Test-step button** (▶) — runs just that cell. For a foreach
  card, that means running the inner pipeline against the cached
  upstream array. For a parallel table, the ▶ button at the
  table level runs the whole row concurrently; each `<td>` also
  gets its own ▶ for testing one cell in isolation against the
  cached upstream `prev`.

### Phase 2 — runner extension

The frozen runner block in `KIND_WORKFLOW_BODY` gets rewritten
around a recursive tree-walker. Schematic:

```
async function runNode(node, prev, ctx):
  if node is <li class="rwa-step"> with single script body:
    return await runStep(node, prev, ctx)
  if node is <li class="rwa-foreach">:
    assert isArray(prev)
    out = []
    for (i, item) of prev.entries():
      innerOl = node.querySelector(':scope > ol.rwa-flow')
      innerPrev = item
      for child of innerOl.children matching .rwa-step:
        innerPrev = await runNode(child, innerPrev,
                                  { ...ctx, iter: {index:i, item, total:prev.length} })
      out.push(innerPrev)
    persist out to node.dataset.lastOutput
    return out
  if node is <table class="rwa-parallel">:
    cells = node.querySelectorAll(':scope > tbody > tr > td.rwa-step')
    results = await Promise.all([...cells].map(td =>
      runNode(td, prev, ctx)))
    obj = {}
    for (cell, result) of zip(cells, results):
      obj[cell.dataset.rwaLabel] = result
    persist obj to node.dataset.lastOutput
    return obj
```

- Pin short-circuit applies before the type dispatch (pin always
  wins).
- Dirtiness recompute traverses the tree post-execution.
- Test-step button works at any node level (step, foreach card,
  parallel table) — runs that subtree against the closest
  cached upstream.
- Error containment: any thrown error propagates up the tree
  walker as in v0.2, with the failing node's `.error` class set.

**Size:** 2 days.

## Open decisions

1. **Workflow product spec doc — yes / no.** Recommend yes (Phase 1
   default). The grammar is non-trivial enough that humans
   reviewing v0.4 changes need a single canonical reference.
2. **Loop `prev` contract.** Recommend Option A: `prev = item`
   (familiar from `Array.map`). Alternatives: B `prev = upstreamArray`
   (item via `ctx.iter.item`), C `prev = undefined`. A wins on
   readability for non-programmers.
3. **Parallel cell label.** Recommend explicit `data-rwa-label`,
   required, snake_case validated. Alternative: derive from
   `<h3>` text (slugified). Explicit is clearer and decouples
   visual label from key.
4. **Parallel error default.** Recommend fail-fast (`Promise.all`).
   v0.5 adds `data-allow-failure="true"` per cell for
   `allSettled`-style. Don't ship both modes in v0.4 — choose one,
   document, iterate.
5. **Pin scope on foreach.** Pin the *whole* iteration result
   (array). Pinning per-iteration is a v0.5 idea if needed.
6. **Test-step on parallel table.** ▶ on the table level runs
   the whole row concurrently against cached upstream. ▶ on a
   single `<td>` runs just that cell. Both useful; ship both.
7. **Dirtiness fingerprint for containers.** Recommend: include
   in the container's hash a fingerprint of all contained step
   bodies (concat them). Any inner edit cascades the container
   to `.stale`. Simple, correct.
8. **Mobile parallel rendering.** Recommend: stack to vertical
   on `<720px`. Lose the visual "they're parallel" but keep
   readability. The execution semantics are unchanged regardless.

## What it explicitly won't do

- Multi-row parallel pipelines (cross-column synchronization). v0.5.
- Per-cell failure containment. v0.5.
- Inter-cell communication. Permanent non-goal.
- Branching / conditional execution (`if prev.length > 0`). Push
  it into the step body (`if (...) return prev;`) — no syntactic
  sugar for conditionals in v0.4.
- A graph editor / canvas / drag-to-connect UX. Document remains
  the workflow; tables and nesting are the only structural
  primitives.

## Dependencies

- **v0.3 ships first.** Pin / dirty / test-step extend cleanly to
  v0.4's new shapes; landing them together would 2× the diff
  size and obscure failures.
- Independent from the action/skill layer spec (v0.7) work.
- Independent from the lens evolution beyond what v0.2 ships.
