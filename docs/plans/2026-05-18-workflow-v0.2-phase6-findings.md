**Date:** 2026-05-18
**Methodology:** scripted `chrome-devtools-mcp` against
`file:///tmp/wf-p6.html` generated by `rwa new --kind workflow`.
**Model under test:** LM Studio + Qwen3-VL-30B-A3B-Instruct (local).
The 30B parameter class is roughly the sharpest local model that still
fits in 32GB unified memory; results below should be re-checked against
gemini-3-flash-preview (OpenRouter) and Claude Sonnet before drawing
production conclusions.

## Detailed findings

### 6a — empty-workflow first-prompt

The model trial:
- Attempt 1: emitted `replace_document` without the required `version`
  field. Runtime threw `version_unsupported`.
- Attempt 2: switched to `apply_edits` with the correct
  `version: "rwa-edit/1"`, but anchored the `find` substring inside
  the wf-style frozen zone. Runtime threw `frozen_zone_violation`.
- Attempt 3: emitted a small `apply_edits` that inserted duplicate
  `<header>`, `<h1>`, and placeholder elements *after* the existing
  `<article class="rwa-workflow">` tag. Runtime accepted (no frozen
  zone violation, no shape change), but the result was structurally
  broken (`<h1>` count = 2, `<p class="placeholder">` count = 2,
  `<li class="rwa-step">` count = 0).

The SYSTEM_PROMPT.workflow CRITICAL block (tightened in Phase 6 prep)
correctly emphasized `replace_document` for empty workflows. The
JSON schema in TOOL_SCHEMAS correctly marks `version` as required.
Qwen3-VL-30B still failed to include it. This is a model-capability
limit on this tier.

**Three possible mitigations** for the v0.2 cold-start path; the
choice is product, not substrate:

A. **Substrate-side scaffold helper.** When the lens detects an
   "empty" workflow (placeholder present, zero steps), the runtime
   synthesizes the scaffold (`<article>`, `<header>`, empty `<ol>`,
   `<footer>`, both frozen zones) locally and the agent is only
   asked to add step `<li>`s via `apply_edits`. Trades model
   autonomy for reliability. Most invasive of the three.

B. **Pre-seeded empty-workflow with one stub step.** Ship
   `rwa new --kind workflow` with a single empty `<li class="rwa-step">`
   already inside `<ol class="rwa-flow">`. The cold-start path then
   uses `apply_edits` to fill in the stub or insert siblings —
   never `replace_document`. Smallest change: one fixture in
   `cli/src/seed.mjs`. Loses some of the "blank slate" feel of the
   empty placeholder.

C. **Stronger model.** Retest against gemini-3-flash-preview,
   Claude Sonnet, GPT-5. If they reliably include the `version`
   field, document Qwen3-VL-30B as below the floor for cold-start.
   No code change.

**Recommendation:** start with (C) — it costs nothing and tells us
whether we're solving a model issue or a substrate issue. If
(C) shows the gap persists across strong models, ship (B); it's the
cheapest substrate change. (A) is reserved for after we have v0.3 UX
polish queued.

### 6d — reorder via prompt

The model emitted a syntactically valid `apply_edits` envelope that
the runtime accepted (no frozen zone violation, valid anchors, no
shape change). But the result was not a swap. The doc length grew
by 683 bytes — likely the model duplicated one step's substring
into another location. Reorder via two `(find, replace)` pairs is
inherently tricky: you need to remove A from one place and insert
it elsewhere atomically, and apply_edits applies edits in order
where find #2 might no longer match after find #1 changes the doc.

`apply_dsl_plan` would handle this cleanly (`delete` + `insert` are
separate ops, each compiled to a unique-anchor edit). The model
chose `apply_edits` despite the SYSTEM_PROMPT_RULES preference of
"structural change → apply_dsl_plan." Either:
- Sharpen the prompt around reorder specifically, OR
- Cut the model some slack and add a "reorder via drag" gesture (the
  v0.2 UX design already calls for this — see Phase 4 visual
  gestures). The visual handle is a backup for cases where prompt
  reorder fails.

The visual drag handle for `<li class="rwa-step">` is implemented
(in the workflow body's runner block), so users have an out today.

### 6c — terse remove fails

`/remove the first step` made the model emit text-only
("I will use `apply_dsl_plan` to delete..." then `finish: "stop"`,
no tool call). The 30B model has weak adherence to the
SYSTEM_PROMPT_RULES' final line ("Always call a tool"). Richer
prompts that name the tool work.

This is a documentation hint for users, not a substrate fix. The
status `✗ model declined` correctly surfaces the case.

### What worked well in v0.2

- The `apply_edits` path for step edits (6b) and remove (6c) is solid
  — single tool call, exact-substring anchors held, frozen zones
  untouched.
- The runner script (real-work node 6e + credential prompt 6f) is
  product-correct: HTTP fetch, JSON.stringify output rendering,
  `prev` threading, sessionStorage-cached credentials all work
  through the unmodified frozen runner block.
- The substrate-level guarantees held throughout:
  - 0 false positives (no edit was wrongly rejected)
  - 0 false negatives (no malformed envelope was accepted as-if-good)
  - frozen zones survived every committed edit byte-identical
  - data-rwa-id auto-injection ran on every commit

## Recommendations for follow-up

1. **Cold-start path** — pick A/B/C per §6a. Likely: retest with
   gemini-3-flash-preview first, then decide.
2. **Reorder gesture-first** — the drag handle (already implemented)
   should be the primary affordance for reorder; the prompt path is
   a fallback. Update the workflow product docs to reflect this.
3. **Tool-call adherence** — Qwen3-VL-30B is below the floor for
   tool-only output. Either bias the system prompt harder
   ("Never respond text-only unless you literally cannot proceed")
   or document a recommended-model list per backend.
4. **`apply_dsl_plan` adoption** — empirically the 30B model picked
   `apply_edits` for a structural reorder (where DSL would have
   worked). The DSL spec writeup (§12) already shows pro models
   under-pick `apply_dsl_plan` at ~1%; this confirms the same shape
   at smaller scale.

## Out-of-scope but observed

- `replaceDocument`'s `frozenZonesIntact` check is strict but
  correct: the test had to bypass it by writing directly to IDB to
  install fixtures with frozen zones. Documented as an acceptable
  test-only seam.
- `data-rwa-id` auto-injection on render-from-IDB happens but isn't
  written back to IDB until the next commit. This is fine —
  inserts on the next commit will see the updated IDs since
  `getDoc()` reads live DOM.
