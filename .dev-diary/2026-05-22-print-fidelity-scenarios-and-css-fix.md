# Print fidelity scenarios — and the bugs reading the PDFs found

Started from a `/goal` prompt: design thorough test scenarios for printing and save-as-PDF, single-page and multi-page, with page breaks as the load-bearing concern. The runtime's `@media print` block in `seeds/rewritable.html` had been there since the seed shipped but had no test surface beyond manual eyeballing. The existing `pres-13` / `pres-14` / `pres-15` fidelity scenarios cover *edit fidelity* — does the agent preserve print CSS when editing? — not *visual fidelity* — does the rendered PDF actually look right? That second axis is what was missing.

First decision was the delivery format. Page-break behavior is layout, and jsdom can't see layout — it doesn't paginate. So scenarios had to be self-contained `.html` fixtures testable in a real browser, not jsdom assertions like the rest of `benchmark/scenarios/`. Built a single-source-of-truth generator: `benchmark/scenarios/print/generate.mjs` owns a `PRINT_CSS` constant mirroring the seed's print rules verbatim, plus a `SCENARIOS` array, plus a `wrap()` that emits one self-contained `.html` per entry. The fixtures are derived artifacts; the generator is the source of truth. Avoids drift across 23 files when the seed changes.

Catalog came out to 23 scenarios across 9 categories: 3 single-page (placeholder, short prose, receipt), 2 multipage prose, 5 tables (the highest break-risk category), 2 code blocks, 2 lists, 2 figures, 1 runtime-chrome leakage check, 3 @page rule scenarios (default margin, document override, named pages with cover + body + page counter), and 3 edge cases (forced break, color preservation, oversize block). Wrote each with a hypothesis line, a manual checklist, and a body that exercises the specific failure mode.

Then wrote `validate.mjs` — a thin headless-Chrome wrapper that prints each fixture to PDF, runs `pdfinfo` for page count and `pdftotext` for content extraction, then asserts per-fixture invariants: `pages == N`, `pages_min`, `present[]`, `absent[]`, `one_page_each[]` (every account number on exactly one page), `same_page[[a, b]]`, `starts_page[[s, n]]`, `no_heading_last_on_page[]`. Avoided puppeteer — `benchmark/package.json` is intentionally jsdom + fake-indexeddb only, and shelling out to local Chrome is cheap. The longer-term puppeteer design lives in `_runner-spec.md` for when pixel diffs become worth the dep.

First validation run: 22 of 23 passed. The one failure was `list-01-long-list-breaks-between-items` at 30 items — fit on a single page on Letter, didn't exercise the page break it claimed to test. Bumped to 50 items so it overflows even on the narrowest reasonable paper. Then the user asked me to put the PDFs side-by-side with the source HTML for easy comparison; switched the output dir from `os.tmpdir()` to `benchmark/results/print/`, matching the existing benchmark/results convention, and added `results/print/` to `benchmark/.gitignore`. Now `scenarios/print/<id>.html` and `results/print/<id>.pdf` sit next to each other by basename — open both in Finder, or `diff -r` two runs after a CSS change.

Committed the lot as `test(benchmark): print-fidelity scenarios — 23 HTML fixtures + headless-Chrome validator`. Auto-mode blocked `git push origin main` (the classifier was treating direct-to-main as bypass-PR-review), but the project's whole history goes direct to main, so the user typed the push themselves through the `!` shortcut.

The pivotal moment came when the user asked "how good is the printing working for multipage documents?" — qualitative, not binary. The 23/23 passing was meaningless without looking at the actual rendered output. So I read the PDFs visually with Claude's PDF reader: `mp-01` long prose, `mp-02` heading-near-break, `tbl-02` 25-row table, `pg-03` named pages with cover + counter. They looked good. Page breaks at paragraph boundaries, H2s with their content, table rows intact, the `<thead>` repeating on each continuation page (browser default, didn't have to ask for it), cover page with `@page :first` margin:0 and a black backdrop, page numbers via `counter(page)` in `@bottom-center`. The hardest case (named pages) worked flawlessly. Reported back with concrete observations from the rendered PDFs, including the one wart I noticed: `tbl-02` page 1 had 85% whitespace because `break-inside:avoid` on a table bigger than a page makes the engine move the whole table to a fresh page before accepting the break.

Then the user pointed at my own "not yet exercised" list — long unbroken strings, deeply nested mixed content — and said write tests for those too and see what happens. That's where the loop actually paid off.

Added five more scenarios: `edge-04` long URL in paragraph (in `<a>` and bare text), `edge-05` long lines in `<pre>` (curl command with bearer token), `edge-06` long hash plus German compound word, `edge-07` table-in-list-in-blockquote (deeply nested), `edge-08` rich content in table cells (paragraphs, lists, code blocks inside `<td>`). Ran the validator — text-only assertions passed except for one literal-text mismatch in `edge-04` that turned out to be a pdftotext artifact (URL wraps at hyphen, extraction sees `internal-\ntools.example.com` not `internal-tools.example.com`).

Reading the rendered PDFs is where the bugs surfaced. `edge-05` was a real, user-data-losing bug: the curl example's long lines were clipped at the right margin in print. `pre { overflow-x: auto }` gives you a horizontal scrollbar on screen and silent truncation on paper. The `sk-proj-1234567890ABCDEF...` bearer token was cut after about 80 characters. A user printing the doc would get an unusable PDF without knowing data was missing. `edge-07` was the same `break-inside:avoid` quirk I'd seen on `tbl-02`, but worse: the entire blockquote moved to page 2 to stay intact, leaving page 1 with H1 + intro and 85% blank space — bad enough that it counts as broken pagination, not just inefficient. `edge-06` was borderline — the hash fit on Letter by luck, but a slightly longer string or A4 paper would push it past the right margin. No `overflow-wrap` rule means we're relying on browser defaults to find break points.

Wrote the print CSS fix. First pass: `overflow-wrap: anywhere` on `p, li, td, th, code, a, pre`, plus `white-space: pre-wrap; overflow: visible` on `pre`, plus remove `blockquote` from the `break-inside: avoid` selector list. Validator ran — two failures. `edge-08` regressed dramatically: the `<th>` "Step" became "St / ep" stacked vertically, "Action" became "Acti / on", "Detect" became "Dete / ct". The narrow table columns shrank to break short words at any character, because that's what `overflow-wrap: anywhere` does — it allows the engine to consider any character as a break candidate when computing intrinsic minimum column width, so a 6-char column will happily break a 4-char word.

That's where the lesson sharpened. `overflow-wrap: anywhere` and `overflow-wrap: break-word` look interchangeable in the docs but differ in a specific way that matters here: `anywhere` reduces the minimum content size used for intrinsic sizing (the column can shrink to a single character); `break-word` keeps minimum content size to the longest word and only triggers breaks when actual overflow would otherwise happen. For body text in a flowable layout, `break-word` is the right choice. For `pre`, which already has a fixed line structure and no narrow-column concern, `anywhere` is correct because a really long token in a code block has to break somewhere or it's lost.

Walked back the rule: `overflow-wrap: break-word` for `p, li, td, th, code, a`; `overflow-wrap: anywhere` only for `pre`. Re-ran. All 28 pass, narrow table headers render cleanly again ("Step" stays "Step"), long pre lines still wrap correctly, blockquote sparse page is gone. Visually re-verified `edge-05`, `edge-07`, `edge-08` to be sure.

Mirrored the seed change into the validator's `PRINT_CSS` constant (the one source-of-truth for fixture generation), regenerated all 28 fixtures, ran `tools/regenerate-refs.mjs` to update `hello.html` and `re-write-able-spec.html` from the patched seed. Added a CHANGELOG entry walking through the three fixes and explaining the `anywhere` → `break-word` walkback so the reasoning isn't lost.

The lesson the session earned: text-only PDF assertions are blind to visual overflow. 23/23 passing meant nothing for `edge-05` — the bearer-token clip was a *visual* failure, but pdftotext extracts text from the underlying PDF object regardless of whether it was rendered inside or outside the paper bounds. The validator's job is regression detection on things you've already characterised; finding new bugs in print rendering needs eyeballs (or, when puppeteer eventually lands, pixel-level checks).
