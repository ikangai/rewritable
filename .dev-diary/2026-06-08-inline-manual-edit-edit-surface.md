The user wanted to edit a rwa document by hand — change a block, delete a block, not just add after it like the lens does today. My first job was to figure out what was actually missing, because the lens already has a 2×2 model and I didn't want to rebuild something that existed. Two Explore passes settled it: change and delete already work, but only through `/edit`·`/delete` slash commands, which call the model. The thing that didn't exist was editing by hand with no model at all. And the happy surprise — the R5 non-agent commit path (`runtimeApplyEnvelope`→`commitCore`, actor `user:edit-surface`) was already load-bearing under the datatable, so this was a UX surface over plumbing that already shipped, not new substrate.

The user picked the ambitious option at every fork: in-place `contenteditable`, double-click to enter (single-click still anchors the lens), Enter commits. Before writing the design up I ran a verification workflow — three readers plus one adversarial skeptic, all against the real seed in jsdom — to nail the one thing that makes or breaks it: how a hand-edit on one block becomes a valid rwa-edit/1 envelope. That paid for itself immediately. The three readers all concluded "no risk." The skeptic, told to actually break it, found two corruption modes none of them tested. First: if you build the replace from `wrapDirectText` or live `outerHTML`, the block's `data-rwa-id` gets dropped or mangled, and on commit `injectMissingBlockIds` assigns a brand-new random id — silently breaking every `#id` fragment link pointing at that block. Second, worse because it's invisible: a `contenteditable` block ends up holding `<div>`/`<br>` soup even with plain-text paste, and `<p>a<div>b</div>c</p>` passes every guard — reserved-substring, `computeShape` (which only counts scripts/styles/top-level types), tag-balance — then reparses on the very next render, the `<div>` hoists out of the `<p>`, the regex source-map sees one `</p>` while the live DOM has five anchorables, and from then on every click anchors the wrong block.

Both fixes live entirely in how the replace string is synthesized, which is why the apply pipeline needed zero changes. `serializeLeafSafe` walks childNodes emitting only escaped text and `<br>`, flattening everything else to its textContent — the soup never reaches storage. And rather than reconstruct `<tag id>` (the design doc's first sketch, which I had to correct mid-build — it drops `class` and everything else), I slice the block's original opening tag verbatim out of `currentDocCache` and re-emit it, so id and every attribute survive untouched, and it's immune to whatever `contenteditable` itself adds to the live node. The editable set also shrank during the build: I'd promised the user `figcaption`, but it isn't independently anchorable — it lives inside `<figure>` and the outer-wins descent never records it — so ordinal resolution can't target it, and it had to go.

Then the code-reviewer agent caught two more, both of which jsdom had been hiding from me the whole time. My empty-deletes-the-block check was `newText.trim() === ''`, which is true in the test because the test sets `textContent = ''`, but a real browser leaves a lone `<br>` when you backspace a block empty, and `'<br>'.trim()` isn't empty — so in an actual browser you'd commit `<p><br></p>` instead of deleting. And there was no no-op guard: an accidental double-click then click-away committed an identity edit, burning a ⌘Z frame and a history record and the dirty flag, which directly contradicted the "blurs with no change commits nothing" line I'd just written into the lens spec. I'd reflexively trusted the green test suite; jsdom's threadbare contenteditable and Selection support meant several of my "passing" tests were passing for reasons that won't hold in Chrome. I pushed back on exactly one review note — dropping the per-edit `reason:'edit'` — because the closest sibling, the lens anchored path, carries a per-edit reason too, so keeping it is the consistent choice, not the inconsistent one.

The lesson that carries forward: a green jsdom suite is not a green browser. The two worst bugs in this feature — id loss and soup desync — were both invisible to every non-adversarial reader and to the test harness, and only surfaced because someone (the skeptic, then the reviewer) was specifically asked to reason about what a real `contenteditable` produces and what the parser does to it on the next render. When the test environment is a weak emulation of the real one, the adversarial pass isn't optional polish; it's where the actual bugs are.
