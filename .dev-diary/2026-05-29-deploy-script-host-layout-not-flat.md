# Writing the deploy script — the host isn't "flat," it's a repo-root mirror with cruft

The user asked whether everything was pushed and deployed, then asked for a sync script. Git was the easy half: `main` was 0 ahead / 0 behind `origin/main`, no modified tracked files, and the long `git status` list was all untracked scratch (`.access-test`, demo HTML, scratch PDFs, `cli/skills/`). So git was clean; deploy was the open question.

I leaned on the deploy memory note and the 2026-05-22 diary entry, both of which describe the prod host as a "flat file sync, not a git checkout" where plain `docker compose up -d --build` from `/opt/docker/rewritable` works. That entry's author had been bitten assuming a `service/` subdir layout and walking it back to flat. I took "flat" at face value and started writing the script around it — and that framing turned out to be misleading enough that I nearly shipped a script that rsync'd files into the wrong places.

The repo's own Docker setup contradicts "flat": both compose files use `build: context: ..` with `dockerfile: service/Dockerfile`, and the Dockerfile COPYs `service/server.js`, `service/public/`, `seeds/`, `demo/html-effectiveness/`. So the build context is the repo root, and the in-image layout mirrors the repo. That can't coexist with a literally flat host directory unless the host has a hand-modified Dockerfile/compose. I couldn't reconcile the two, so I refused to guess and had the script's `preflight` step inspect the real host before any transfer. My own attempt to SSH in read-only got blocked by the auto-mode classifier (production reads need explicit user approval naming the prod target) — which is correct; the script is for the user to run with their own access, so the block didn't matter for the deliverable.

The user ran `preflight` and pasted the output, and that's where "flat" dissolved. `/opt/docker/rewritable/` is the build context (`build: .` in the host's `docker-compose.yml`), and underneath it the layout actually mirrors the repo: the *live* server is `service/server.js` (24509 bytes, dated 17 May — byte-for-byte the repo's), `service/public/` holds the real assets, and `seeds/` + `demo/` sit at the top level. The "flat" appearance came from two stale decoys sitting at the top level next to everything else: `server.js` (2650 bytes, 29 Apr) and `public/` (29 Apr). Nothing COPYs those — they're pre-flattening cruft that the earlier diary author saw, read as "the layout," and described as flat. They're dead weight, not inputs.

I had the user `cat` the host's `Dockerfile` and `docker-compose.yml` to kill the last guesswork. The Dockerfile is byte-identical to the repo's `service/Dockerfile` (same four COPY lines). The compose differs from the repo's `docker-compose.prod.yml` only in spelling — `build: .` instead of `context: .. / dockerfile: service/Dockerfile`, with the traefik apex+share routers, `rwa_shares` named volume, and external `router_web` network all intact. Functionally the same image, same `rewritable-new` container.

That collapsed the script from its hedged first draft (configurable `COMPOSE_DIR`/`COMPOSE_FILE`, shipping Dockerfile+compose into a `service/` subdir that doesn't exist on the host) to something exact: rsync only the four content paths the Dockerfile actually consumes — `seeds/`, `service/server.js`, `service/public/`, `demo/html-effectiveness/` — via `rsync -R` so repo-relative paths land at their host paths, then `cd /opt/docker/rewritable && docker compose up -d --build` (no `-f`, because the host's active file is plain `docker-compose.yml`). I deliberately left the Dockerfile and compose out of the automated sync — on the host they live at the top level, not under `service/` like the repo, so a naive rsync would drop copies where the build ignores them — and documented the manual `scp` for the rare infra change. I dropped `--delete` too: orphaned old assets are harmless since the server reads files by name, and `--delete` risks removing host files the script doesn't own. Verification curls `/health` and asserts `/rewritable.html` is 200, contains `id="rwa-bootstrap"`, and exceeds 100 KB — the same live-seed check the 2026-05-22 entry landed on.

The lesson that carries forward: a prior diary entry is evidence, not ground truth. The 2026-05-22 "flat layout" note was an honest read of stale top-level decoy files, and trusting it would have produced a wrong deploy. The build context's own `COPY` lines are the real spec for what ships where — when a procedural note and the Dockerfile disagree, inspect the host and believe the Dockerfile.
