# 2026-06-04 — SNAPSHOT-01 jsdom teardown race

Picked up the one red on main: the conformance suite crashed at SNAPSHOT-01 with `TypeError: Cannot read properties of null (reading '_location')` deep inside jsdom's `Window.js`. The first thing that misled me was the scenario name — the crash prints under SNAPSHOT-01, so the instinct is to read snapshot-01.mjs. But snapshot-01 only does raw `applyEdits`/`replaceDocument` calls, all awaited, all landing in `commitDoc` which fully awaits its IDB transaction. Nothing there leaks async work. So the crash couldn't originate where it surfaced.

The stack pointed at `Window.js:615` — jsdom's `queueMicrotask` wrapper, which on a thrown callback calls `reportException(window, e, window.location.href)`. Reading `window.location` after `window.close()` is the actual crash: `_document` is null. So the real failure is a *masked* error inside a deferred callback firing on a torn-down window, and the crash I saw was just jsdom's error reporter dying while trying to report it. I instrumented `window.queueMicrotask` to capture the masked error and a scheduling stack before re-throwing. That paid off immediately: the dying microtask was scheduled by `commitCore`, the real errors were `getElementById`/`createElement` on `undefined`, and the tag said `scenario=SKIN-02 windowClosed=true`. The callback belonged to SKIN-02 — the scenario that runs *right before* SNAPSHOT-01 — and fired during SNAPSHOT-01's `harness.fresh()` boot wait, after SKIN-02's window was already closed.

SKIN-02 commits a skin through `commitCore` and breaks its poll loop the instant `getDoc` shows the skin — which is at `renderDoc`, before `commitCore`'s trailing `await rwaBumpDirtyCount()` and its Fix-I2 `queueMicrotask(emitRuntimeEvent)`. So the scenario calls `ctx.dispose()` (synchronous `window.close()`) while the commit tail is still suspended. The tail resumes post-close, touches the gone `document`, throws, and jsdom crashes reporting it. Pure harness teardown race — in a real browser the window never closes mid-flight, so guarding the runtime would mean adding product code for a test-only artifact. The fix belonged in the harness.

First fix attempt: defer the close to `setTimeout(() => window.close(), 0)`. Ran it. Still crashed. That was the instructive part. I'd assumed deferring by one macrotask would let the microtask queue drain first, but I hadn't reasoned about *which* macrotask. fake-indexeddb schedules request completion on `setImmediate` (I checked `lib/scheduling.js` to confirm, rather than guess again). In Node's loop the timers phase (`setTimeout`) runs *before* the check phase (`setImmediate`) within an iteration — so my `setTimeout(0)` close fired before the IDB completion that resumes `commitCore`. Wrong primitive entirely. I measured the tail with a throwaway script: from the scenario returning to the last deferred microtask firing was one `setImmediate` cycle. So the fix is to drain a few `setImmediate` cycles against the live window before closing (each `await setImmediate` also flushes the microtask queue, so the trailing emit settles too). Four cycles for headroom over a measured tail of one. 84/84, stable across repeated runs. Landed as f2458e2, benchmark-only.

The lesson that carries forward: when deferring teardown to outlast async work, the macrotask *phase* matters — `setTimeout(0)` and `setImmediate` are not interchangeable, and fake-indexeddb lives in the check phase, so you drain it with `setImmediate`, not `setTimeout`. And a crash that names a scenario isn't necessarily caused by it; a deferred callback from the previous scenario's closed window can surface under the next one's name.
