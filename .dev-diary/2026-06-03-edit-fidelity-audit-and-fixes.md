The goal was to make sure edit fidelity is 100% and edits have no unintended side effects, testing with a real model through the bridge. I started where the signal is cheapest and most trustworthy: the deterministic suites. Conformance was 82/82 and stub fidelity was meanS=2.00/meanT=2.00/drift=0 across all 108 scenarios. So the substrate, given a correct envelope, already applies edits with zero drift. That reframed the whole task — the question wasn't "does the apply path corrupt things" (it doesn't, `apply_edits` is an exact find/replace splice), it was "what happens when a real model generates the envelopes."

Getting the bridge to run took two false starts. The benchmark's `bridgeModel` POSTed to web_cli_bridge and got a 401 — the bridge gained token auth after the May RCE fix and the benchmark client never sent an Authorization header. Added `RWA_BRIDGE_TOKEN`. Then exit 127, `claude: command not found` — the bridge is a GUI-launched process with a bare `/usr/bin:/bin` PATH, so homebrew's `claude` isn't visible. Added `RWA_CLAUDE_BIN`. Then the auto-mode classifier blocked the call because the benchmark's bridge command carried `--permission-mode bypassPermissions` — which I removed, because the bridge agent only emits a text envelope and needs no tools, and it was the exact anti-pattern the shared seed's `bridgeCommand` already dropped. After that a single smoke call returned a clean `{find:"Hello",replace:"Goodbye"}`.

The first real-model screen looked alarming: meanT well below 2, several scenarios at T=0 with non-trivial drift. ID-02 was the clearest — S=2 (heading renamed, id preserved, aria resolves) but T=0, drift=0.23. I built a throwaway diagnostic to dump the envelope plus a fixture↔result diff, and the truth was the opposite of a side effect: the model's edit was `find='>HEADING_TEXT Original title</h2>'`, `replace='>Updated title</h2>'`, and the actual changed bytes were only the heading text. The `>`, the `</h2>`, the `id="heading-3"` were all byte-identical. The model had padded its anchor with surrounding context — which the system prompt explicitly tells it to do, "extend with surrounding context if not [unique]." The bug was in the oracle: `computeDriftFromEdits` measured the full `edit.find` span against the expected region instead of the bytes that actually changed. A safe uniqueness tactic was being scored as a side effect.

The fix was to strip the common prefix and suffix shared by `find` and `replace` to get the effective changed core, and score that. I convinced myself it was safe before touching it: the core is always a subset of the full find span, so the change can only narrow a measured span, never widen it — no scenario that was drift-0 could regress, and the stub run confirmed it stayed 2.00/2.00/0. And it still catches a genuine co-modification, because if the model also edits adjacent bytes the core widens to cover them (I pinned that with a test where a padded anchor changes both an in-region word and an out-of-region sibling — drift stays positive).

Somewhere in here the load-bearing insight landed: because `apply_edits` is an exact splice, the runtime *cannot* change bytes outside the model's envelope. So any "successful edit with drift" can only mean the model targeted a region the scenario under-declared, or the model itself over-edited — never the substrate. That made the conclusion robust regardless of how the rest of the numbers fell. I ran the full 108 through the bridge with the fixed oracle and classified every imperfect scenario. The four remaining S=2&T<2 "suspects" all triaged to artifacts: BULK-03 used `apply_edits` instead of the prompt's requested `replace_document` (rename correct, scenario penalizes tool choice); CONT-02 renumbered footnotes correctly with a one-edit list rewrite while the scenario's expected regions encoded the stub's two-edit decomposition; INTL-02 and INTL-06 simply no-op'd, and an unchanged document obviously has no side effects — the drift=1 there is the `!envelope.edits` fallback mis-scoring "no edit" as "maximal drift." Zero genuine substrate side-effects across the whole screen.

Then shannon, stress-testing the lens in a real browser, flagged a real one I'd never have found through the bench, because the bench drives `modify()` directly and never exercises click-to-anchor. `buildSourcePositionMap` descends into TABLE to record each `<td>` as its own anchorable entry, but `anchorableOrdinal` and `liveNodeForEntry` stopped at the TABLE. So once a document had a table, every ordinal after it was shifted by the TD count — clicking a paragraph after a table anchored to a cell's source range, and a subsequent anchored edit would splice into the wrong element. That one's an actual unintended side effect, squarely the goal. The fix was to mirror the TABLE descent into both live walks so all three agree; I exposed the two walks for tests and pinned the symptom shannon described (post-table `<p>` resolves to its own slice, logical entry tag equals the highlighted element's tag, and `<td>` is now directly anchorable instead of a -1 no-op), then regenerated hello.html and the spec reference from the seed.

What carries forward: a drift-vs-declared-region metric is a proxy for "no side effects" that quietly breaks the moment a real model anchors differently than the hand-written stub — the real guarantee is structural (exact splice), and the benchmark had been crying wolf. The honest measure is the bytes that differ between find and replace, not the width of the anchor.
