Started the session on administrative work — landed the v0.5 / v0.6 / v0.6.1-patch antecedents alongside the v0.7 working-method companions into `docs/specs/`, confirmed the v0.10 main spec hadn't drifted, then drafted the action-layer implementation plan against the R7 audit. About forty minutes in, the conversation turned to workflows. The user asked what skills give workflows that workflows can't have on their own. I leaned skill-layer-first — composability, auditability, dev-loop sanity — and the user pushed back almost immediately: don't overcomplicate this; the lens is the editor, the visual is the manifestation, the JavaScript lives inside each node the user prompts into existence, skills wait for later. That set the design constraint for the rest of the day — workflow as a substrate-level product type, not an above-the-substrate skill orchestration.

I built v1 around an `<article class="wf-canvas">` with a `<section class="wf-nodes">` of `<article class="wf-node">` cards, each carrying an inline `<script type="text/workflow-node">` for its JS body, plus six frozen zones around the wrappers to keep the structural skeleton honest. The first end-to-end test against LM Studio with Qwen3-VL-30B failed before producing any output: every node-add tripped `structural_shape_changed`. The substrate's `computeShape` was counting the data-bearing workflow-node scripts toward the doc's executable-script count. Fix was small — exempt non-executable MIME types — but the symptom was that the design and the substrate's shape rule were in collision. Then the runtime broke on the model's preferred function-expression body (`async function(input) {...}`) where it had only handled bare statement bodies; I made the runtime tolerant of both shapes. Then the empty placeholder kept persisting because the model sometimes skipped the delete step; I made it CSS auto-hide via `.wf-nodes:has(.wf-node) .wf-empty { display:none }`. Each fix was real and shipped; the v1 commit ran end-to-end. Multi-node ordering stayed flaky.

The user came back: "really? didn't work. try it yourself." I drove chrome-devtools-mcp manually and confirmed the rough edges — the node-add path worked, but the surrounding shape (the model improvising new wrappers, the ordering drift) made it feel like fighting the model on every edit. I drafted a v1.5 plan with a sentinel anchor inside the editable region, structural frozen zones around the canvas opening and closing tags, and a rename to "pipeline" since v1 was really linear and "workflow" oversold it. The plan looked like more bandages on a shape that wanted out.

I sat with the v1 design and the user's earlier direction together and noticed they disagreed. The user had said the visual IS the manifestation — the structure should be apparent from looking at it, both for humans and for the agent. v1's `<article class="wf-canvas">` with custom-MIME inline scripts and six frozen zones was the opposite of that: every edit had to thread around explicit substrate guardrails. I pivoted to a wholesale redesign — `<ol class="rwa-flow">` of `<li class="rwa-step">` cards, each step's body in `<script type="text/rwa-step">` wrapped in `<details>` for collapse, an `<output>` slot for the last-run result, a step contract of `async function run(ctx, prev)` so dependencies were explicit, and exactly two frozen zones (the `<style>` block and the trailing runner script). The `<ol>`/`<li>` ordering is well-formed because ordered lists are ordered; the shape carried its own invariants.

The UX design landed as `docs/plans/2026-05-18-workflow-ux-design.md` and the six-phase implementation as `docs/plans/2026-05-18-workflow-v0.2-implementation.md`. v1.5 was marked superseded but kept in history as drafting context — the conformance-coverage thinking from v1.5 carried over. v0.2 shipped across four commits: substrate Phases 1-3 (the new `KIND_WORKFLOW_BODY` plus a rewritten `SYSTEM_PROMPTS.workflow`); Phase 4 visual gestures (drag-to-reorder, ×-delete, +-insert-between, native `<details>` show/hide, Run) plus a substrate addition — `runtime.applyEnvelope(envelope, options)` — so client-side gestures commit through the same audit log as agent edits, distinguished by a `surface` label; Phase 5 conformance scenarios (42 → 46, with two new SHAPE tests guarding the script-type exemption from the v1 work); Phase 6 manual verification.

Phase 6 surfaced something useful. Against LM Studio + Qwen3-VL-30B, five of seven scenarios passed cleanly — edit, remove, GitHub fetch through CORS, credential prompt + cache, ⌘S + reload survival. Two failed: the empty-workflow scaffold (model called `apply_edits` instead of `replace_document` despite the prompt explicitly saying replace_document for empty workflows), and reorder via prompt. The substrate matrix was clean — zero false positives, zero false negatives. The failures were in what the model emitted, not in what the substrate accepted. I wrote up the findings with three mitigations (substrate scaffold helper, pre-seeded stub step, stronger model) and recommended retesting against the substrate's default model first. Switched to `google/gemini-3-flash-preview` via OpenRouter and reran both failures. Both passed. No substrate change needed.

The user asked about n8n at the end. I went through their editor surface — pinData on a per-node basis so you don't re-fetch live APIs during iteration, dirtiness indicators that turn red when an upstream node changed, a "Test this step" button that runs just the current node against pinned upstream output. That trio maps cleanly onto the linear pipeline: tighten the iteration loop by an order of magnitude without changing the spec or adding layers. Drafted `docs/plans/2026-05-19-workflow-v0.3-iteration-tightening.md` as the next bundle.

The lesson is the one from the v1 → v0.2 pivot. v1's individual bugs all had real fixes, and I shipped them. But the reason the substrate kept fighting the agent was that the shape was wrong, not the rules. Semantic HTML — `<ol>`, `<li>`, `<details>`, `<output>` — encodes the structural invariants in the elements themselves; explicit wrapper guards encode them in the substrate's bookkeeping. When the substrate keeps having to defend its invariants against routine edits, the shape isn't carrying them.
