Picked up the `rwa edit` CLI work in the post-implementation phase — eight plan tasks were already committed and 73 tests were green. The question was whether the surface was actually ready to ship, not whether it compiled. So I drove an adversarial pass before touching anything else. Built a sandbox at `/tmp/rwa-adversarial`, generated fresh containers via `rwa new`, then fed `edit` deliberately broken envelopes through stdin: wrong envelope version, unterminated `INLINE_DOC`, edits whose `replace` injected a `data-rwa-id="hacked"` attribute, edits targeting the `#rwa-doc-mount` selector inside the bootstrap, multi-edit batches that changed the doc's structural shape. Every probe surfaced the right structured failure with the right exit code. The reserved-substring check caught the `data-rwa-id` injection at validate time, before any splice happened, which was the failure mode I was most worried about.

Then I dispatched a cross-task code-review subagent and let it audit the whole `rwa edit` surface against the design doc and the v1 plan. It came back with three things worth fixing. The interesting one was atomic-write durability: the implementation did `writeFile(tmp)` then `rename(tmp, dst)`, which is atomic on POSIX for the rename itself, but on power loss between the rename and the kernel's page-cache flush, the destination inode would point at a tmp file whose contents hadn't been persisted yet — you'd get an apparent success and a zero-byte or truncated file on recovery. The fix was to swap `writeFile` for an `open` → `writeFile` → `datasync` → `close` → `rename` sequence on the temp file, so the contents are durable on disk before the rename publishes the new inode. `datasync` rather than `sync` because tmp-file metadata durability isn't load-bearing — only the data behind the rename target matters. The other two were smaller: a misleading line in `cli/README.md` claiming the apply layer retries on failure (it doesn't; retries live in the agent loop, not in the splice path), and a missing note in `cli/TODO.md` that attribute-form `data-rwa-frozen` enforcement is intentionally scoped down in the CLI v1 — the marker-form `<!-- rwa:frozen:begin/end -->` is enforced and the reserved-substring check catches `data-rwa-frozen` in `find`/`replace` payloads, but the parser doesn't honor the attribute-form on existing HTML. Landed all three in one commit (`d5919b7`).

The user came back hours later with "update the readme, release notes and commit everything. then push it." That was the third phase. Wrote a new "Updating in place" section into the top-level `README.md` between "Getting a fresh file" and "Sharing a snapshot" — three terse examples covering the instruction / piped-envelope / `--plan` paths and a pointer to `cli/README.md` for the reference. Prepended a `2026-05-19 — rwa edit: programmatic edit CLI` entry into `CHANGELOG.md` covering v1 scope, the exit-code contract, atomic write semantics, and the known v1 scope-downs. Split the commits along clean lines — one for the archived design + implementation plan in `docs/plans/`, one for the user-facing README + CHANGELOG announcement — and pushed `f4ff739..3ecbecf` to `origin/main`.

Between phase two and phase three the user also asked me to run the `claude-automation-recommender` methodology manually against the repo. I located the skill in the plugins marketplace tree, read its three reference markdown files directly rather than invoking the skill, then walked the codebase: settings, deps across the four subprojects, CI, doc structure. The recommendations were what you'd expect for a zero-dep vanilla-HTML project — keep CI minimal, the test harness is already good, the `cmp`-before-`cp` pattern in `prepublishOnly` is exactly the right shape for the canonical/snapshot dsl-compiler split. Not a code-changing pass; an inventory.

The lesson from the day is the value of the adversarial pass before shipping. The code-review subagent caught real things the unit tests couldn't — the fsync gap was invisible to any test that didn't crash the kernel mid-call — and the adversarial probes confirmed the surfaces I was nervous about. Both passes ran in under an hour together. The cost of catching the fsync issue post-publish would have been a CHANGELOG entry plus a point release; the cost of catching it pre-publish was twelve lines of code and one comment explaining why `datasync` not `sync`. The discipline is to do this before the docs commit, not after.
