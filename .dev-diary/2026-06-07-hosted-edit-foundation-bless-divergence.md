Picked up the session as "verify/review the repo state first" and it turned into building the whole hosted-edit foundation. The verify part was quick — main was green across every offline suite, and I fanned out six readers to confirm the CLAUDE.md claims against the actual code rather than trust them; zero code drift, only low-severity doc drift (the skill-host §2-vs-§1.3 contradiction, a stale csp-boot count). Martin then picked Thread 4, the writable hosted runtime, as the thing to build.

The design fork that mattered came early. Martin wanted the live editable projection to serve the *real* current.html with a shim that redirects the seed's own commit to the server — "served file + shim." So I read the seed before committing to it, and the read killed the naive version: the lens/⌘K calls the internal modify() (5397), which applies and commits through closure-private applyEdits/replaceDocument/commitDoc, and RWA itself is a closure const (331). An injected script can't reach any of it. So a pure commit-redirect shim is impossible without touching the seed. I surfaced that, and we settled on the smallest thing that works: one additive, guarded seam — `if (window.__rwaCommitSink) {...}` at commitDoc (the single funnel both the agent and direct-text paths bottom out in), byte-identical when the flag is unset, same discipline as runtimeRegionCommit's frozenBypass. I told the group chat "one seed seam."

Then I built it subagent-driven — eight tasks, a fresh implementer plus a spec reviewer plus a code-quality reviewer per task, fixes looped back through re-review. That went smoothly through Task 5. The vendored apply pipeline (copying cli/src into service/lib byte-identical, cmp-gated, because the deploy ships service/ only) and the store/auth/modify/undo all came up green with the reviewers catching real things — a history-kind heuristic that disagreed with the seed on a DSL escape op, an overloaded histLen field.

Task 6 is where the lesson lives. The projection plus shim passed every jsdom unit test and both reviews — the unit test even computed the shim's baseHash and the server's baseBodyHash over the same string and asserted equality. Looked done. But I'd promised myself a real-browser e2e because the spec reviewer flagged that the seed-boots-shim-before-bootstrap loop is something jsdom can't actually reach, so I ran one model-free, driving runtime.applyEnvelope in a real Chrome against the local service. It failed. Every hosted edit came back 409 stale_base and never landed. The unit tests were green and the integration was broken.

The reason: the seed's boot step blesses data-rwa-id onto anchorable blocks with *random* ids and writes the blessed doc back to rwa_doc (6140), so the browser's currentDoc — the thing the shim hashes — carried ids the server's stored, never-blessed body didn't. The two sha256s could never agree. The unit test passed precisely because it hashed one string twice and never ran the boot blessing. Worse, a read-only investigation surfaced a second vector: the agent is told to copy data-rwa-id verbatim into its find/replace strings, so even with the hash fixed, applying an agent envelope against an un-blessed server body would find_not_found. That second fact is what killed the obvious fix (strip the ids before hashing) — you can't, the ids are load-bearing in the envelopes. Server-side blessing was the other option but it meant replicating the seed's exact anchorable-block selector parser-free and keeping it cmp-pinned forever, brittle. So the one-seam plan became two: a second guarded seam, `window.__rwaSuppressBlockIds`, that skips boot blessing in hosted mode. That closes both vectors at once — the hosted body stays un-blessed (hash parity) and the agent reads an un-blessed doc (no ids in envelopes), and it's the natural fresh-rewritable state anyway, self-blessing on first local open. Re-ran the browser smoke: 200, chained edits, undo, reload-sync all passed.

The holistic pre-merge review then caught that the vendored apply path only *comments* the MAX_DOC cap (a pre-existing CLI scope-down I'd inherited), so I enforced it in the handler rather than the byte-identical mirror, and it flagged that serving /r/:id path-keyed on the apex origin shares sessionStorage across hosted docs — a narrow cross-doc token-exposure that /s/ shares already avoid with per-subdomain origins. That became a documented deploy gate. Merged --no-ff to local main; galois's telegram Phase-B doc landed inside my coordination window and auto-merged clean since it was file-disjoint.

The thing that carries forward: a unit test that stubs the boundary it's verifying will pass a broken integration. The shim/server hashes matched in jsdom and diverged in the browser because only the browser ran the seed's boot. For anything that spans the seed↔runtime↔server loop, the real browser is the test, not jsdom.
