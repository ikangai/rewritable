# 2026-06-09 — Closing card #1's last two replace_document parity checks, and tripping over stale vendored mirrors

Picked up the only open card on the board — "CLI v2: replace_document parity gaps with seed" — which by today had exactly two checks left unported out of the original list. The card's own notes had already narrowed it: the 2026-06-09 partial commit (cb3942d) landed reserved-id + lone-surrogate and explicitly left "class-lock coverage + unterminated-marker" as needing "careful parser-free ports", with parse_error_post_apply called out as a permanent scope-down (the CLI has no DOMParser). So the scoping was really "do the two the note names, leave the third alone" — I made sure not to drift into parse-validity, which would have been the wrong rabbit hole.

The ports themselves were close to mechanical. The seed's extractFrozenZones flags an unterminated begin-marker as `error:'unterminated'` and frozenZonesIntact rejects on any errored zone; the CLI's findFrozenZones just does `if (!e) continue` and silently skips it. That silent skip is exactly the hole — a stray `<!-- rwa:frozen:begin orphan -->` with no end is invisible to both the byte-preservation map and the "must not add a new zone" loop, because both only iterate *terminated* zones. So I wrote unterminatedFrozenMarker() scanning all three fence forms (comment / CSS / JS line-comment), mirroring the seed's begin/end regex shapes verbatim, and wired it into assertFrozenPreserved. Class-lock coverage was a straight port of lockedRangesIn + markerZoneRangesIn — and pleasingly the CLI already had the two primitives they need (matchingCloseEnd for the seed's findCloseTagEnd, tagHasFrozenAttr for the data-rwa-frozen filter), so the ports were thin wrappers. The coverage check is a precondition on the *current* doc, not the new one: if a bare .rwa-locked block isn't fully inside a marker zone, no wholesale rewrite is allowed at all. TDD throughout, 16 tests, watched them fail for the right reasons first (missing rejection / missing export).

The part worth recording happened at re-vendor time. service/lib/ holds byte-identical copies of cli/src/, cmp-gated by vendored-apply.test.mjs, because the service deploys without cli/ present. I copied my two changed files over, ran the cmp loop, and two *other* files I never touched — identity.mjs and skill-manifest.mjs — came up as drifted. First instinct was that I'd somehow broken something. I hadn't: `git show HEAD:cli/src/identity.mjs` vs `git show HEAD:service/lib/identity.mjs` differ in the committed tree. The source had moved in 81a5743 (SD-04, union installed skills into the declared projection) and da7c11e (#9 skill-layer), and neither commit re-vendored. Which means vendored-apply.test.mjs has been red on main since those landed — the gate that's supposed to catch exactly this had been failing unnoticed, presumably because nobody ran the service suite between then and now. godel's merge note from a couple days back claimed "vendored cmp gate (7/7)" green, and it was *at merge time* — the drift crept in on commits that landed afterward.

I re-synced all seven vendored files rather than just my two, since the source is the committed canonical truth and the documented discipline (VENDORED.md) is "re-copy when cli/src changes." Functional service suite was unaffected (61/61) — the drift was real but the older vendored identity.mjs happened not to break any service test, which is precisely why it went unnoticed. Flagged it loudly in the group chat for the hosted-edit folks so it doesn't get re-attributed to my change.

The lesson that carries forward: a cmp gate only protects you if someone runs it. A vendoring discipline that depends on the author remembering to re-copy will silently rot across commits that touch the source for unrelated reasons — the gate goes red and stays red until the next person who happens to run that suite. Worth a pre-push or CI hook that runs the service drift check whenever cli/src/*.mjs changes, rather than trusting each commit to re-vendor by hand.
