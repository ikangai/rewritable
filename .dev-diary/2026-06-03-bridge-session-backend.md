# 2026-06-03 — bridge-session backend (modifyViaSession)

Came in to add two things from a four-day-old design note in the web_cli_bridge repo: a `modifyViaSession` backend that talks to the bridge's new persistent `/session/*` endpoints, and a `renderDoc(persisted)` fix in `modifyViaBridge`. First job was orienting in a seed I didn't write — four copies of rewritable.html (seeds/ canonical, hello/spec/root regenerated from it), a jsdom test harness, and the existing single-shot bridge backend.

The renderDoc fix turned out to be already done, and I almost made it anyway before reading carefully. `applyEdits` and `replaceDocument` now `return commitDoc(...)`, and `commitDoc` returns `persistDoc` — the post-`injectMissingBlockIds`, post-`canonLF` bytes — so `renderDoc(newDoc)` is already rendering the persisted form. The DOM, the IDB store, and any staged copy already agree. The note predated the edit-fidelity audit that made `commitDoc` return its persisted text. So the right move was to not touch it and say so.

The real problem surfaced when I lined up `modifyViaBridge`'s prompt against the bridge's `build_turn_prompt`. The single-shot prompt ends with "output ONLY a single JSON envelope as your last response, no commentary." The bridge's per-turn prompt says the opposite: read the staged doc from this path, WRITE the envelope to a file via .part→rename, then reply DONE. Two output channels, flatly contradictory. So I couldn't reuse the single-shot prompt verbatim as the session instruction — `buildSessionInstruction` is the single-shot body (system rules + the inlined doc + the three envelope shapes) with exactly the stdout-channel sentence removed, letting the bridge own the file channel. The user chose max-fidelity (keep the doc inlined for parity with the audited prompt) over the lean "don't re-send the doc" option, so the doc rides in both the typed instruction and the staged file; the cost is that a very large doc gets typed into the tmux composer, which is slow.

Then the auth asymmetry. `/run` is tokenless today — `modifyViaBridge` sends no Authorization header and the deployed bridge runs without a token. But `/session/*` is token-mandatory and origin-allowlisted on the bridge side (the loopback-RCE defense from the May audit, now enforced per-route). So `modifyViaSession` needed a Bridge Token setting the single-shot path never had. And `/session/create` needs a server-side working directory a browser can't possibly know, so I added a Session Dir setting too. Two settings the bridge path doesn't carry — honest friction, surfaced in the settings hint rather than papered over.

One trap I'd have shipped without thinking: the bridge appends a `<!-- rwa:gen <uuid> -->` sentinel to the doc claude reads, so it can reject a stale write. For `apply_edits` that's harmless — the anchors are content, the sentinel is a trailing comment claude never targets — but a `replace_document` echo would carry that reserved `rwa:` comment straight into the stored document. So `applyParsedEnvelope` strips the sentinel from a `replace_document` doc before it reaches `replaceDocument`.

The mocked tests were straightforward except the SSE. Rather than wire `ReadableStream`/`TextDecoder` into jsdom, I made the mock responses omit `resp.body` so `consumeSessionStream` falls through to `resp.text()` — the block parsing, which is the part worth pinning, runs identically either way.

The live end-to-end was the satisfying part and had its own snag. I went to start my worktree bridge on 8765 and hit "address already in use" — the installed v0.3.1 menu-bar bridge owns the port and answers `/session/list` with 501, because it predates the endpoint. I didn't want to kill the user's running app, so I ran my bridge on 8799 and a test-only `html.replace` repointed the seed's hardcoded `BRIDGE_URL` there. node's `fetch` — which I'd wired in as `window.fetch` — sends no Origin header, so the origin allowlist was moot and the bridge treated it as a non-browser caller; and the pre-existing IPv6 `*:8799` listener didn't collide with my IPv4 `127.0.0.1` bind. Real claude appended the exact marker I asked for, and the whole loop closed: `modifyViaSession` → real bridge → real claude → `applyEdits` → `renderDoc`, marker present in the doc.

When two halves of a system each want to dictate the output channel — one prompt says "print the envelope to stdout," the other says "write it to a file" — reusing a prompt across them isn't a transport detail you can ignore; the conflict lives in the instructions, and the fix is to let exactly one side own the channel.
