# 2026-05-21 — Bridge wiring for the fidelity runner + Opus vs gemini side-by-side

Continued from the bug hunt earlier. The next move was extending coverage rather than fixing — the autoresearch:scenario pass produced 50 situations across 10 dimensions, all framed as Input → Expected → Notes. Most overlapped existing conformance scenarios, but ten of them were genuine gaps: batch ordering with anchor invalidation/duplication (SEQ-02/03), replace_document parity around adding zones / unterminated markers (AUTHOR-06/07), `id="rwa-doc-mount"` (CONFORM-17), parallel `tool_calls` in one response (CONFORM-18), `$&` / `$$amount` literals via splice (EDGE-11), combining-mark non-normalization (EDGE-12), `parseBridgeEnvelope` ANSI tolerance (EDGE-13), and the MAX_REPLACE inclusive boundary (EDGE-14). I wrote all ten as conformance scenarios matching the existing shape — `harness.fresh()` per scenario, `expectRwaError` for failure paths, `getDoc`/`getUndoStack`/`getHistory` for IDB inspection. The suite went 62 → 72 passing on the first run, no iteration needed; the patterns were unambiguous enough that the matches landed correctly.

Then the user asked to run the tests with `google/gemini-3-flash-preview` — that's a fidelity run, not conformance, because conformance is jsdom-stubbed and doesn't take a model. The fidelity runner already supports `node runners/run-fidelity.mjs <model>` against OpenRouter, so it was just `npm run fidelity -- google/gemini-3-flash-preview` after sourcing `.env`. 108 scenarios × N=3 (mostly), 12 minutes wall, meanS=1.66 meanT=1.30. Better than the prior gemini-3.5-flash baseline (1.62/0.63), notably on stability — the model touches fewer bytes outside intended changes.

Then the pivot: "use the bridge for the next test." The bridge backend is wired into the SEED RUNTIME via `modifyViaBridge` — POST to `127.0.0.1:8765/run` shelling out to `claude -p` — but it wasn't wired into the benchmark runner. The runner's `selectModel` dispatched `stub` → `baseline` → fallthrough to `openRouterModel`, no third option.

I almost reached for option B: set the seed's backend to `bridge` in the harness and let `modifyViaBridge` fire actual fetch through the harness's fetchHandler stub, with a pass-through for localhost:8765. That would have exercised the seed's bridge path verbatim. The reason I didn't: the seed's bridge path is one-shot and doesn't fit the `openAiCompatChat` retry loop, so the fidelity runner — which schedules N=3 runs per scenario through `modify()` — would be measuring the wrong thing. The runner needs a model abstraction that returns `{tool_calls, usage}` in OpenRouter shape regardless of what the model actually is.

So I went with option A: a new `bridgeModel` factory in `benchmark/runners/model.mjs` that masquerades as an OpenRouter model. It synthesizes a single prompt from the multi-turn message history (`[ROLE]\ncontent` per message, with `[TOOL RESULT for call X]\npayload` for retry feedback), base64-encodes it for shell safety, POSTs `{command: "echo ... | base64 -d | claude -p --output-format json --permission-mode bypassPermissions"}` to the bridge URL, parses the JSON-formatted response, walks the `result` text for a balanced `{tool, envelope}` object via a mirrored `parseBridgeEnvelope`, and returns it as if it were a single tool_call. Stateless across calls — claude -p starts a fresh session each invocation — which means the retry loop's accumulated `messages[]` carries the failure context forward into each fresh prompt.

One choice that diverged from the seed: I used `--output-format json` instead of `--output-format text`. The seed uses text because its `parseBridgeEnvelope` walks raw stdout for the envelope. I used json because the fidelity runner needs token usage for its tok_in/tok_out telemetry. The result field inside the json wrapper still contains the same model text, so I walked THAT with the same `parseBridgeEnvelope` logic. Same parse path, plus usage. The seed would do the same thing if it wanted telemetry.

Smoke-tested with a hand-built three-message conversation — "Old → New" — and it came back in 4.9s with a clean `apply_edits` envelope. Then `npm run fidelity -- bridge`, archived the gemini TSV first so it wouldn't get overwritten. 41 minutes wall, 108/108 completed. meanS=1.68 meanT=1.60 — narrow win over gemini-3-flash-preview's 1.66/1.30. The headline number isn't the interesting one.

The interesting numbers are by tag and by scenario. Opus is markedly more stable on content edits (meanT=1.66 vs 1.27) — fewer unintended byte changes when it stays surgical. But Opus escapes to `replace_document` on RTL/CJK content (INTL-01/02/03/05/06 all drift=1.0, where gemini stayed on apply_edits) and on PRES-07/PRES-09 — it picks "rewrite the whole doc" over surgical edits when the byte boundaries get fuzzy. The drift=0 median hides this because most scenarios are 0; the affected ones jump straight to 1.0. Token counts looked weird for bridge (tok_in=6 or 18 instead of ~1500) — that's claude -p reporting `input_tokens` as differential beyond the cache hits, not total input. The ~34k cache-read tokens from Claude Code's preamble don't show up in the field. Token totals between bridge and OpenRouter aren't apples-to-apples; meanS/meanT/drift are the comparable signals.

The shared weak spot: `failure_mode` tag scores ~0.60 meanS on both Opus and gemini. The multi-turn correction pattern — recovering from `find_not_unique` / `frozen_zone_violation` / `structural_shape_changed` via tool_result feedback — is hard for both. Worth noting because it's a model-class limitation, not a model-quality difference. The protocol's retry loop helps, but the model still has to use the feedback well.

Wired the bridge knob in idiomatically — `selectModel` dispatches `bridge` before the OpenRouter fallback, `RWA_BRIDGE_URL` overrides the default 127.0.0.1:8765, 360s per-call timeout. Anyone with web_cli_bridge running can now do `npm run fidelity -- bridge` and compare local Claude against any OpenRouter model on the same 108 scenarios.

When a runner has an "I am the OpenRouter API" abstraction, plug new providers in at that boundary even when the real backend behaves differently — masquerading is cheaper than threading a new dispatch path through the runner.
