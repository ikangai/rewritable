The user asked to create a presentation with `rwa new presentation` and hit "rwa: no rwa file in ./ is labeled presentation". My first instinct was that the presentation kind didn't exist yet and I'd be building it. I ran the brainstorming skill and sent an Explore agent through `seeds/rewritable.html` and `cli/src/seed.mjs` to map it — and the instinct was wrong. The presentation kind is already complete: `KIND_TABLE.presentation` in `cli/src/seed.mjs` ships a real three-slide starter, and the seed carries a first-party 'presentation' view provider (spec §5.10) with a Present toggle, h1/h2-boundary slide wrapping into `<section class="rwa-slide">`, arrow/PageUp-Down nav, and a print path that flattens the deck back to linear. `rwa new --kind presentation` works today and `tests/view.mjs` covers it.

So the failure wasn't a missing feature — it was a dispatch overload. Commit 2460277 taught `rwa new <word>` to treat a bare first word as a template name and scan the cwd for a `data-rwa-template="<word>"` file. That path now shadows the built-in kind names: `presentation` (and `workflow`, `document`) get routed to template-clone, find nothing, and error, instead of resolving to the kind. The natural command form collides with the template feature that a newer commit introduced.

I drafted an AskUserQuestion about precedence — template-first, kind-first, or error-message-only — and the user rejected it to widen the frame. What they actually want is intent-driven input: `rwa new presentation` reading naturally without flags, and beyond that `rwa write blog post about the rewritable architecture`.

That reframed the whole thing. The two examples aren't the same beast: "presentation" is a noun from a closed set (kinds ∪ cwd templates) that code should route by lookup, while "write a blog post about X" is free-form intent where the model should only generate content, not route — which is exactly what our own Rule 5 says. The deciding constraint turned out to be the CLI's own offline-first guarantee: `rwa new` must work without network, so an agentic command can't fold into `new` without breaking that promise. That forces a two-verb split — keep `new` as an offline deterministic scaffold and give it bare-word kind resolution, and add a separate online `write` that is `new` plus the existing `rwa edit` agent loop. Templates fall out as user-defined kinds, so one resolver serves both verbs. I left the user with the open fork: a deterministic prefix-match for the leading kind, which I lean toward, versus a model-classified intent parse, plus the question of what to name the agentic verb.

No code yet — this was discovery and design, and the decision is still pending the user's answer on the fork. The lesson that carries forward: when a natural command fails, check whether a newer feature quietly claimed its syntax before assuming the feature is missing. The presentation kind was there all along; the later template-dispatch rule from 2460277 was eating the command.
