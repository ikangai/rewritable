The ask came as a goal with three parts: bump the default model to `google/gemini-3.5-flash`, make the editing UX feel fluid, and surface what the model is doing in real time the way Claude's app does — an animated status line above the input. The user attached a screenshot of Claude.app with the chip reading something like "Referenzdocs/card-schema.md ⟳" in small grey italics above the textarea. That was the visual reference.

I started by reading the lens region of `seeds/rewritable.html` to map what already existed. The default lived at line 249 as `RWA.MODEL:'google/gemini-3-flash-preview'`. Status feedback was split across three things: `setStatus` for the top-right pill, `setPalSt` for the legacy ⌘K palette footer, and a pulse-dot in the lens chrome driven by a `data-busy` attribute. I assumed the pulse-dot was the lens-side feedback and would just need text added next to it — but when I traced the call sites I found the dot was only set inside `runAnchoredCommand()`. The main `modify()` path (slash commands with no anchor) and `modifyViaBridge()` (claude -p) never touched it. So the user's actual experience for the most common edit path was: type, press ⌘+Enter, wait silently for several seconds, document changes. That's the UX hole, more than the absence of a fancy chip.

Pivoted to designing a single `setLensProgress(state, msg)` helper that the three agent paths would all call into. State drives both color and the leading glyph: spinning grey ring for `thinking`, a green ✓ for `done`, a red ✗ for `error`. I gave the `done` state a 1.4s auto-clear so it fades after the document re-renders, and let `error` stick until the next modify overwrites it — successes should be ephemeral, failures should persist long enough to actually read them. Removed the old pulse-dot CSS but left the `data-busy` attribute assignments in place; they don't drive anything visible now but they're harmless state telemetry for any external observer that might watch them.

The progress copy was the next decision. Generic "Working…" felt useless — the screenshot showed Claude's chip naming the actual artifact, which is what makes it informative. For rwa the natural granularity is the tool call: `apply_edits`, `apply_dsl_plan`, `replace_document`. I wrote a `friendlyToolName()` mapper — "edits", "structural plan", "full rewrite" — so the chip reads `Applying edits…` rather than the wire name. Between attempts the chip shows `Retrying (attempt 2/3)…`, which is honest about what's actually happening and gives the user a reason for the latency.

Wired the helper into all three paths. The `modify()` loop sets `Thinking…` before the API call and switches to `Applying <name>…` once the tool call comes back. `runAnchoredCommand()` got the same treatment. `modifyViaBridge()` says `Asking claude -p…` because that subprocess has a ~5-10s cold start and otherwise looks dead. On the way through I also surfaced the "no API key" branch into the chip — previously that error only landed in `setPalSt` which the lens doesn't show.

For the model side, the bump itself was mechanical: change the default in five places — the seed, `cli/src/import-vision.mjs`, the `rwa edit` fallback in `cli/bin/rwa.mjs`, the help-text default in the same file, the `cli/README.md` flags table, and the `service/public/build-skill.md` skill doc. The interesting move was pre-populating the OpenRouter datalist. Before, the datalist was only filled when the user clicked Test (which only works for ollama/lmstudio against `/v1/models`); OpenRouter users got an empty input. I added a `OPENROUTER_MODEL_SUGGESTIONS` constant of seven IDs drawn from `benchmark/results/` — models that have actually been exercised on this codebase, not random picks — and populated the datalist whenever the OpenRouter backend is selected. So now the input has real autocomplete out of the box.

Verification ran in three layers. The 291 e2e tests, 246 lens tests, and 62 conformance scenarios all passed unchanged. The one CLI test failure was an attribute-form frozen-zone enforcement that's been a documented `test.todo` since the rwa-edit CLI shipped — unrelated to anything I touched. Then I opened the regenerated `hello.html` in Chrome via the DevTools MCP and called `setLensProgress` from the console to actually look at each state. The thinking and applying states rendered as expected; when I tried to screenshot `done` it had already auto-cleared by the time the screenshot fired, which was an unexpectedly nice confirmation that the timer is the right length.

Regenerated `hello.html`, `re-write-able-spec.html`, and `rewritable.html` from the seed via `tools/regenerate-refs.mjs` so the bootstrap stayed byte-identical-except-for-INLINE_DOC across all reference docs.

The lesson worth carrying forward: when adding a new code path, the first question to ask isn't "what should the UI for this look like" but "what did the existing UI cover and where were the gaps." The pulse-dot answered the surface-level question — there *was* a busy indicator — but missed that two of three agent paths didn't drive it. The user's "UX should be fluid" complaint wasn't about the indicator design; it was about the silence.
