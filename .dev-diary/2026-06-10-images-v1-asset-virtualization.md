# 2026-06-10 — images-v1: inline bytes, virtual tokens, drag-drop GUI

Goal-hook session: get images into rewritables without giving up the single self-contained file, and make the GUI feel effortless. I started by exploring and almost talked myself into the obvious architecture — an `rwa_assets` IDB store with a second serialized slot next to INLINE_DOC — before three facts killed it. First, docx import already emits images as inline `data:` URIs and they survive render/commit/⌘S today, so the storage problem was already solved by accident. Second, OPFS, which the spec nominates for binary blobs, is unavailable under `file://` — the primary way rewritables open. Third, a second serialized slot breaks the load-bearing "bootstrap is byte-identical except INLINE_DOC" invariant and drags buildFile, the CLI seed mirror, the vendored service libs, and the hosted seams along with it. The real problem was never storage; it was that `buildUserPrompt` ships the whole doc to the model, so one 500 KB photo is ~170K tokens, and the 8 KB `MAX_REPLACE` cap makes any edit that quotes an `<img>` tag fail. So the design became: bytes stay in the doc, and every agent boundary virtualizes `src="data:image/…"` to `rwa-asset:<hash8>` tokens, with the apply core expanding tokens back after validation. Caps measure the token form — they're a text budget, not a pixel budget.

Two wrinkles surfaced while writing the plan that the design doc had missed. The non-agent GUI insert path has the same cap problem — a 200 KB URI in an envelope `replace` trips MAX_REPLACE — so `runtimeApplyEnvelope`/`commitCore` had to learn an `assets` option and the insert envelopes travel in token form too. And `commitDoc`'s hosted sink reconstructs envelopes from `rwa_hist` and POSTs them to the server, which applies on real bytes — so sink-bound envelopes must be expanded back, and hosted+images stays a documented limitation (the server's vendored 8 KB cap). I also chose FNV-1a over the design's SHA-256 for the token hash: `crypto.subtle.digest` is async and missing in jsdom, and the token is identity/dedupe, not integrity.

Implementation went in TDD phases against a new `tests/image-assets.mjs` (blocks A–G, 83 checks): round-trip identity first (expand(virtualize(doc)) must be byte-equal — everything stands on that), then opts threading through applyEdits/replaceDocument, then the three agent boundaries, then the GUI. One genuinely new failure mode got closed along the way: a no-assets writer inserting a fresh `rwa-asset:` token would have committed a permanently broken image silently; `assertNoNewAssetTokens` now rejects it, while tokens that pre-existed in the doc stay legal so a pre-broken doc remains editable. The orphan-tolerance set exists for the same reason. Block D proved the scary case concretely — before the anchored-path change, a model response with an invented token committed verbatim.

Two false alarms cost time. `datatable.mjs` went 43/3 mid-session and looked like my regression; it was the fresh worktree missing `cli/node_modules` (the suite shells out to `rwa edit`), made worse by my shell's cwd drifting between root and worktree so consecutive runs contradicted each other. And four block-G failures turned out to be `commitDoc`'s data-rwa-id backfill decorating the inserted `<figure>` — correct behavior, exact-string asserts too strict.

The browser proof was worth it: dropped a synthesized 4000×3000, 2.1 MB JPEG into a real Chrome `file://` container and watched the ladder produce a 1600×1200 WebP at 206 KB, toast included; the 1×1 PNG took the keep-original path; undo and reload-persistence held. Merged to local main 7ce4949 — disjoint by design from kay's uncommitted CLI card, which is also why the CLI mirror (`apply-edits`/`agent-loop`/`edit`) and service re-vendor are still open: those files sit dirty in the shared checkout and the multi-agent protocol says don't edit around in-flight work. Pinged kay three times; the gate is documented in the plan (tasks 12–13) and in CLAUDE.md's new Images routing entry.

The lesson that carries forward: when a feature looks like a storage problem, check whether it's actually a boundary problem — the bytes were fine where they were; only the model's view of them needed to change.
