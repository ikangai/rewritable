User asked me to run a whole-codebase security analysis with the security-guidance plugin. My first instinct was to launch `autoresearch:security` — STRIDE + OWASP, structured report folder, the works. The user corrected me: they specifically wanted `security-guidance@claude-plugins-official`, not the autoresearch tool. Read the plugin's README and its hooks.json. The plugin is reactive — three hooks, all diff-shaped: `PostToolUse` on Edit/Write for regex pattern warnings, `Stop` for an LLM diff review of what just changed, and `PostToolUse` on `Bash(git commit:*)` for an agentic review of a commit. There is no "scan the whole codebase" mode. The investigation method lives in `review_api.py`'s `AGENTIC_INVESTIGATE_SYSTEM` constant but it's a method expecting a diff, not a codebase.

So I split it. Layer 1 — the regex pack in `patterns.py` — is just data; wrote a small driver that imports `SECURITY_PATTERNS` and runs it across every tracked file using the same matching logic `check_patterns()` uses. Got 67 files with at least one rule match. Triaged: 38 `innerHTML_xss` hits were almost all noise (markdown specs with code examples, demo fixtures, vendored pdf.js), and the 28 `new_function_injection` hits were similar. The real production sites — `seeds/rewritable.html` (the bootstrap), `service/public/import.html` and `new.html`, `cli/src/seed.mjs` and `seed-extract.mjs` — were all expected: documented designs where the dangerous primitive is the intended one. Layer 1 produced no new findings.

Layer 3 was where the work was. Took the plugin's `AGENTIC_INVESTIGATE_SYSTEM` prompt as my own methodology — entry points, sinks, source-to-sink trace, parser/validator differentials, the "high-miss patterns" list including allowlist-semantic-escape and under-validated-sink-args. Walked the service, the CLI, the seed runtime, and the browser-side import in that order. Service was mostly clean — `validateContainer` is permissive by design (rwa containers are arbitrary HTML), the rate limit trusts the leftmost `X-Forwarded-For` (acknowledged in source comments), `Host` is echoed unvalidated into the share URL response.

Then I hit the bridge backend in `seeds/rewritable.html:3435-3462`. `modifyViaBridge` builds a prompt by concatenating the system prompt, `buildUserPrompt(instr, cur, frozenZones)` (which embeds the entire current document between `<DOC>…</DOC>` tags), base64-encodes it for shell safety, and pipes it through `claude -p --output-format text --permission-mode bypassPermissions`. The base64 quoting is fine — that's not the issue. The issue is `bypassPermissions` — it tells Claude to run without prompting for bash, file write, anything. And the document body in the prompt is attacker-controlled when the document came from a published share or a hand-passed file. Any prompt-injection text in the document gets fed to a Claude session with full local shell. Cracked open RCE-via-document.

Looked for the same shape in the CLI. Found it in `cli/src/import-claude.mjs:159-211` (`runClaude`): `rwa import file.pdf --claude` spawns `claude -p --permission-mode bypassPermissions --add-dir <dir> <prompt>`. The prompt tells claude to use the `pdf` skill on the input file. The skill extracts text from the PDF, the text becomes part of the running conversation, and prompt-injection text inside the PDF can hijack the session. The source comment at line 20 is candid: *"The user already trusts their input file (they're importing it)"* — but that's the wrong threat model. People run `rwa import` on files they received from third parties; that's the whole point of an import command.

So two Criticals — and they both close with the same one-flag change: drop `--permission-mode bypassPermissions` from both invocations. Default permission mode in `claude -p` prompts the user before each tool use, which is the right safety posture for a backend the user can't directly see.

Rest of the findings filled in a familiar pattern. CWE-598 on `--open` passing the OpenRouter API key via `?key=` in a `file://` URL (visible in process listing, shell history, OS open logs before the bootstrap's `history.replaceState` scrubs it). Symlink-race on `cli/src/edit.mjs:164`'s predictable `${filePath}.rwa-tmp-${pid}` if anyone runs the CLI on a shared filesystem. `convertHtml` in `cli/src/import.mjs` lets imported HTML scripts through with a stderr warning while the markdown converter sanitizes — asymmetric and surprising. No CSP or HSTS on apex responses.

Wrote the report inline in the response rather than creating a `security/` directory — CLAUDE.md Rule 3 (surgical changes), and the security-guidance plugin doesn't have an output-directory convention anyway. Cleaned up my `/tmp/sg_scan.py` driver at the end.

The plugin's diff-shape is fine for what it does — turn-by-turn defense during a Claude Code session — but it isn't a static analyzer. The prompts in `review_api.py` are general enough to repurpose as a methodology, though. The two Criticals are the same bug at two call sites: an autonomous-agent transport with `bypassPermissions` will always be a prompt-injection RCE wherever attacker-influenceable input reaches it.
