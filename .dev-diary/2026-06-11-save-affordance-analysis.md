Started analyzing the tension between our IndexedDB working state and the current `cmd-s` behavior, which triggers a file download. I used grep to hunt through `seeds/rewritable.html` for existing save logic like `rwa_fsa`, `showSaveFilePicker`, and `dirty` states, as well as UI copy related to `⌘S` and nudges. I also checked `re-write-able-spec.md` to see how we defined File System Access (FSA) semantics. The initial analysis in `docs/plans/20gan-06-11-save-affordance-framings.md` confirmed that true in-place saving is restricted by browser policy, as a page cannot hold a write handle to its own backing file. I then explored the idea of "download checkpoint" or "create backup" terminology and checked `seeds/rewritable.html` for `INLINE_DOC` hydration sites. I initially worried that downloading a new version would create a mismatch between the user's local edits and the downloaded file, but found that because our working state is keyed by `DOC_UUID` in IndexedDB, the local edits persist on the same machine regardless of which file version is opened next.

The working state lives in IndexedDB, not the file itself.
