The user wanted a kanban board for this project and pointed me at the kanban skill. I initialized it via `bash $CLAUDE_SKILL_DIR/scripts/init.sh`, which dropped a fresh rwa container at `.kanban/board.html` and added `.kanban/` to `.gitignore`. The opening view was empty, as expected — the skill defers content to `kanban add` calls. The user then asked me to seed the board from the diary, plans, and commits, which is the interesting framing: use the project's accumulated history as the source for what should be on the board, rather than asking the user to enumerate it.

Walked the three sources in parallel — `.dev-diary/` (three recent entries: the workflow substrate pivot, the rwa edit CLI adversarial pass, and yesterday's lens progress indicator + gemini-3.5 work), `docs/plans/` (twenty-one entries, with the action-layer implementation and the v0.4 concurrency plan as the newest), and `git log` (a clean run from workflow v0.7 through v0.11, then the rwa edit CLI v1 ship, then the gemini-3.5 + lens chip). Cross-referenced what the plans called for against what the commits had landed. The workflow v0.3 iteration-tightening and v0.4 concurrency-and-iteration plans were both already implemented in the form of commits v0.7 through v0.11 — multi-row parallel, foreach with ctx.iter.parent chains, ctx.signal mid-Run cancellation, container dirty/stale, session-state cache. So those plans are dead-letter from a tracking perspective, even though they still hold history value.

That left two real buckets of outstanding work: the action layer (the v0.7 spec, with a phased implementation plan archived at `docs/plans/2026-05-18-action-layer-implementation.md` — the largest single chunk of upcoming work) and the CLI v1 follow-ups, all of which are documented in `cli/TODO.md`. The TODO entries are the cleanest source of board-worthy cards because they were already pre-triaged by code review: two medium-priority hardening items (the replace_document parity gaps versus the seed validator, and the attribute-form `data-rwa-frozen` enforcement gap), and five low-priority polish items (subcode naming alignment, OPENROUTER_API_KEY env fallback parity, DslCompileError export, EACCES test.todo, uniform onRetry shape). Added all eight cards via the kanban CLI. I deliberately skipped putting the recently-shipped items into a "done" column — the diary and CHANGELOG already record that history, and the board is for forward work.

The CLI calls landed without drama but hit a model-availability hiccup partway through — claude-opus-4-7 was temporarily unavailable, so auto-mode couldn't safety-classify the parallel Bash calls and they got cancelled. Retried serially after a few seconds and they all went through. Worth knowing the auto-mode pattern: parallel calls fail-all when the classifier flakes, so degrading to sequential during transient classifier outages is the right move rather than re-batching.

Then the user said "I don't see cards." This was the substantive moment of the session. The CLI had written the cards into the file's `INLINE_DOC` literal — I verified by grepping for the eight new IDs and confirming the file size jump from ~75K to ~174K. But the user already had the board.html open in Safari from when it was empty. Safari had loaded the empty doc into the per-container IndexedDB at `rwa_368f5a68-…`, and on reload the rwa runtime preferred the IDB copy over INLINE_DOC. The file on disk was current; the browser's view was frozen at the moment of first open.

This is a real friction point of using the kanban skill alongside an already-open board. The substrate is explicit about it — IDB is the authoritative source once a container has been opened, INLINE_DOC is only the seed. CLI mutations don't reach the browser. The mitigations are all on the user's side: open in a private window (fresh IDB), or delete the IDB entry in DevTools and reload. Walked the user through both on Safari specifically: Safari → Settings → Advanced → enable Develop menu, then Develop → Show Web Inspector → Storage → Indexed Databases → delete `rwa_<DOC_UUID>`.

The architectural shape worth carrying forward: the rwa container model assumes the runtime is the single writer to the document state. The kanban skill breaks that assumption — the CLI is a second writer, operating on the file directly, with no IDB invalidation channel back to any open browser tab. The substrate's dirty-state detection runs the other direction (IDB doc newer than INLINE_DOC → unsaved changes) and doesn't help here. If kanban use grows, the skill needs either (a) a mode that operates through the runtime instead of around it, (b) a runtime-side detection that INLINE_DOC has changed since last IDB write and offers to reload, or (c) cleaner UX guidance that "the board is closed while another agent has it" is the expected workflow. Option (b) is the most aligned with rwa's "the file on disk is the durable artifact" stance.

The lesson: when a skill mutates an rwa container's file directly, any open browser instance of that container is now stale in a way the runtime can't auto-detect, and the user will see no change on reload. The CLI-side and runtime-side states are not currently reconciled — and that mismatch shows up as "the cards I just added aren't visible," which looks like a CLI bug but isn't.
