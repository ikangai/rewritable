# 2026-05-20 — Autonomous bug hunt; regex checks drifting from DOM truth

Ran `/autoresearch:autoresearch:debug` against the whole codebase in auto mode. No symptom to start from — the full test suite was green (62/62 conformance, 16 cli apply-edits with one documented `test.todo`, 291 e2e, 246 lens, 108 fidelity stub, 12/12 DSL). The job was "find new bugs in a codebase that already knows about most of its scope-downs," which sounds like fishing but turned up five real ones at LOW severity.

I started by reading the load-bearing surfaces: `seeds/rewritable.html`'s `applyEdits` / `replaceDocument` / `compileDslPlan`, `cli/src/edit.mjs`'s atomic-write block, `cli/src/agent-loop.mjs`, `service/server.js`'s publish flow, and the sanitize/import parity between `cli/src/import.mjs` and `service/public/import.html`. The mammoth URL sanitizer survived everything I threw at it — `javascript:`, `JavaScript:`, percent-encoded scheme tricks, `data:image/svg+xml` smuggling — because SVG-via-`<img>` runs in image mode and URL parsing stops scheme at `%`. The service publish path was clean too: I'd worried about Host-header spoofing producing malicious share URLs, but you need DNS for the spoof to mean anything, and Traefik filters the production case.

The first real hit came from staring at `injectMissingBlockIds`. The function's comment says it skips `data-rwa-frozen` elements, but the implementation only consults `markerZoneRangesIn`, which is named for marker-form zones. I expected a bug there. I wrote a jsdom probe and ran a `<aside data-rwa-frozen>` test — and it correctly skipped the aside. Surprise. Reading `markerZoneRangesIn` again, I saw it ALSO walks a `data-rwa-frozen` attribute regex. Fine, not the bug I expected. But then I tried `<p data-other="data-rwa-frozen">` — same skip behavior. That regex uses `\b...\b`, which matches the substring inside an attribute value. So any element whose attributes mention the literal `data-rwa-frozen` anywhere gets flagged as a frozen zone. False positive; the block loses URL-fragment anchorability. The DOM-based `dataRwaFrozenSnapshot` (line 2761) uses `querySelectorAll('[data-rwa-frozen]')` and gets the right answer. The regex drifted from the DOM truth.

Pattern noticed; I started looking for the same shape elsewhere. `tagBalance` jumped out: opens regex is `<script\b`, closes regex is `<\/script\s*>`. Asymmetric. `\b` between `script` and `-` matches, so `<script-thing>` counts as an open. The closes regex requires whitespace or `>` immediately after `script`, so `</script-thing>` does NOT match as a close. A probe confirmed it: `tagBalance('<script-thing>x</script-thing>')` returns `opens:1,closes:0`. Custom elements with `script-*` / `style-*` prefixes are legal (the spec requires the hyphen), and an `applyEdits` that adds such an element to a previously-balanced doc throws `structural_shape_changed`. Computed-shape via DOM-parse is the real check at line 2961-2963; tagBalance was meant as a token-level fallback for unclosed-script-eats-document scenarios, but its regex went lopsided.

Third one was `parseBridgeEnvelope`'s fence-strip. The regex is unanchored — strips the first ``` anywhere in the buffer, even mid-prose. I thought that would be a real exploit until I traced the brace walker downstream and realized it recovers via balanced-brace tracking regardless of stray fence residue. Logged it as B5 mostly for cleanliness.

The fourth was unrelated to regexes — `idbPut`/`idbGet`/`idbDel` resolve on `request.onsuccess` instead of `tx.oncomplete`. The IDB spec says a put REQUEST can succeed while the TRANSACTION later aborts (quota, FS error), and the caller gets a successful promise while data is rolled back. `commitDoc` itself uses the correct `tx.oncomplete` pattern, so the load-bearing write is fine; the helpers are the inconsistent ones. Affects undo, FSA handle persistence, dirty-count writes, bootstrap id-blessing. Subtle and real.

Fifth was `cli/src/edit.mjs`'s tmp-file cleanup. Cleanup is wired only into the rename-catch — if `writeFile` or `datasync` throws after `open(tmp,'w')` succeeded, the tmp file is left behind. I tried to provoke it (chmod the dir, chmod the file) but macOS's `rename` is governed by directory permissions, so the read-only-file path doesn't trigger it; the leak is theoretical for the brief writeFile/datasync window. LOW severity (clutter, not data loss).

Wrote everything up to `debug/260520-2001-rwa-hunt/` — findings.md (the bugs with evidence and suggested fixes), eliminated.md (the hypotheses I tested and ruled out, so a future hunt doesn't re-walk them), debug-results.tsv (the iteration log), summary.md (executive view). Then added five LOW-priority cards to the kanban. The summary recommended fix order by ROI: B1 (tagBalance) first because it's a one-line regex fix with small blast radius; B4 (idbPut helpers) second because it's mechanical and meaningfully more correct; B2, B3, B5 after.

The lesson: when a regex-based check has a DOM-based sibling, the DOM one tends to be correct and the regex tends to drift. Three of five bugs were that exact shape. Worth a v2 pass to prefer DOM-based checks where both exist.
